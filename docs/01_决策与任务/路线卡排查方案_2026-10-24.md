# 路线卡排查方案：屏幕报"还没有查到路线"

日期：2026-10-24
对应现象：墨水屏显示 标题「路线查询失败」+ 正文「还没有查到路线」+ 底部按键提示
结论一句话：**这不是网络失败，而是链路已经打通的证据。板子确实从公网服务器拿到了响应，只是那个会话下面还没有卡。**

---

## 一、为什么能确定链路是通的（三条硬证据）

不是猜测，是可核对的代码事实。

| 证据 | 内容 | 意义 |
|---|---|---|
| 固件里没有这句话 | `route_card.cc` 的网络失败分支写的是「网络不好，请再试」；整份固件源码里没有「还没有查到路线」这七个字 | 屏幕上这句话不可能由板子本地产生 |
| 这句话只在服务端一处 | 全仓库搜索「还没有查到路线」，只命中 `app/route_card_service.py` 的 `code=3` 分支（会话没有卡时返回） | 这句话是服务器发过来的 |
| 固件只有解析成功才显示 message | `Parse()` 里 `code != 0` 时把 `message` 字段抄进 `source` 显示；而 `Parse()` 只在 `err == ESP_OK && status == 200 && s_len > 0` 之后才被调用 | 说明 DNS、TCP、TLS 握手、证书链校验、HTTP 200、JSON 解析，六步全过了 |

换算成链路：

```
板子 ──DNS──> keleshiyizhimao.com ──TCP:443──> TLS(证书链校验 ISRG X1) ──> nginx ──> 8010 服务
                                                                                    │
                                          {"code":3,"message":"还没有查到路线"} <──────┘
                                                                                    │
                                                    屏幕：路线查询失败 / 还没有查到路线
```

所以**这一屏是成功的一半**：传输层全部通过，剩下的问题全在"会话号对不对得上"。

---

## 二、屏幕文字与结论的对应表

以后看到不同文字，可直接对号入座。

| 屏幕正文 | 实际含义 | 断点位置 |
|---|---|---|
| **还没有查到路线** | 服务端正常应答，该会话没有卡 | 写卡侧（平台有没有调工具、会话号是否一致） |
| 网络不好，请再试 | 请求没成功：`err != ESP_OK` 或 `status != 200` | 板端到服务端（TLS、域名、防火墙） |
| 接口不存在 | HTTP 404 | nginx 的 `location = /api/route-card` 没生效 |
| 响应格式错误 | 拿到 200 但 JSON 坏了 | 响应被截断、或被别的服务接管了这个路径 |
| 内存不足 | 起任务失败 | 板端 RAM，与网络无关 |

---

## 三、剩下的三种可能，以及怎么区分

链路已通，只剩三种可能。判定只靠两个数字：**板子日志里的 `bytes=`** 和 **服务端日志里的 `session_id=`**。

| 可能 | 板端 `bytes=` | 服务端访问日志 | 库里 | 处理 |
|---|---|---|---|---|
| A. 板子没选会话，走的是局域网演示地址 | 不是 44 | 没有这次 GET | 无关 | 板上重新选一次会话 |
| B. 板子带了会话号，但平台没写过卡 | **44** | 有 GET，`session_id` 有值 | 该会话无卡 | 让平台真调 `query_transit`，或先手工造卡验证屏幕 |
| C. 平台写过卡，但写到别的会话号上 | **44** | 有 GET，`session_id` 与库里不一致 | 卡在别的 `session_id` 下 | 把两者对齐（见第五节） |

`44` 这个数字是这次响应的精确字节数：`{"code":3,"message":"还没有查到路线"}` 共 44 字节（7 个汉字 × 3 + 23 字节 JSON 结构）。它是空卡响应的指纹，比任何日志都硬。

## 四、排查步骤（按顺序做，每步都有判据）

### 步骤 1：抓板端串口（最硬的一手证据）

本机已开好监听（900 秒），只需去板子上按一次键：

```
长按中键 → 中键（第 1 项 去医院）
```

手动起监听（若已过期）：

```bash
cd D:/WorkBuddy_Projects/2026上海AI硬件黑客松
D:/ESP_IDF/espressif/python_env/idf5.5_py3.11_env/Scripts/python.exe \
    tools/serial_watch.py --port COM6 --seconds 900
```

要抓的三行，判据写在括号里：

| 日志行 | 判据 |
|---|---|
| `route: request started for selected session` | 有会话走公网。若是 `using demo endpoint`，就是可能 A（没选会话） |
| `https: end err=ESP_OK status=200 bytes=44` | `err=ESP_OK` + `status=200` + `bytes=44` = 可能 B 或 C，链路完全正常 |
| `card state=` / `source='还没有查到路线'` | 固件把服务端的 message 抄到了屏幕上，与照片一致 |

注意：串口被占用会打不开（`PermissionError`）。先把 `idf.py monitor` 或旧的抓包脚本关掉，必要时 `taskkill /F /PID <pid>`。

### 步骤 2：在服务器上拿板子的真实会话号

```bash
# 服务日志（方式一：文件）
grep 'GET /api/route-card' /var/log/route-card.log | tail -5

# 服务日志（方式二：systemd）
journalctl -u route-card -n 200 --no-pager | grep 'GET /api/route-card' | tail -5
```

日志形如：

```
[21:03:11] 127.0.0.1 GET /api/route-card?session_id=xxxx -> 44B 3ms
```

`-> 44B` 与板端 `bytes=44` 必须对得上，这是两端互相印证。**把 `session_id=` 后面那一串抄下来**，它是后面所有操作的目标。

### 步骤 3：一条命令把整件事判完

```bash
cd /opt/route-card/test          # 把 why_no_card.py 传上去，或直接 python3 跑
python3 why_no_card.py
```

它会读服务日志、nginx 日志、sqlite，自动回答"板子要的会话 与 库里的卡 是否同一个"，并直接给出结论和下一步命令。

已知板子的会话号时更准：

```bash
python3 why_no_card.py --board-session <步骤2抄到的会话号>
```

### 步骤 4：把卡直接写到板子的会话号上（最快让屏幕出真卡）

这一步不依赖平台，用来把"板端→服务端→屏幕"整条链路一次验证到底：

```bash
curl -sS -X POST http://127.0.0.1:8010/api/query-transit \
  -H "Content-Type: application/json" \
  -d '{"session_id":"<板子的会话号>","city":"上海","origin_text":"西岸国际会展中心","destination_text":"复旦大学附属中山医院","travel_mode":"transit"}'
```

预期返回 `"code":0`，并且 `/api/route-card?session_id=<板子的会话号>` 从 44 字节变成 252 字节左右、5 行文案。

然后回板子上再按一次中键。**屏幕出 5 行路线，就证明整条链路完全可用**，问题只剩"平台调工具时用的会话号"。

本机已用真实腾讯数据彩排过，实际返回：

```
{"code":0,"title":"去复旦大学附属中山医院(东院区)",
 "lines":["步行610米到车站","乘地铁11号线坐3站","到上海游泳馆换乘",
          "乘隧道二线坐5站","下车步行420米到院"],
 "source":"腾讯地图 50分 换乘1次 21:10"}
```

## 五、如果确认是"会话号对不上"（可能 C）

根因是两套 ID 被当成了同一套：

| 来源 | 会话号是什么 | 谁写的 |
|---|---|---|
| 板子取卡 | 平台上"会话列表"里的那个 ID，用户手选 | 固件从平台拉 `conversations` 列表，选中后存 NVS |
| 平台写卡 | 平台调 `query_transit` 时传的 sessionId | 服务端从 `params._meta` / `arguments.session_id` / `Mcp-Session-Id` 头里猜 |

服务端目前是"四处捞"（`_identities()`），因为平台的真实字段名我们还不确定。解法只有两条：

1. **看 raw_log 定字段名**：`curl -sS http://127.0.0.1:8010/api/admin/raw?n=5`，把平台真实请求的 headers 和 body 看清楚，然后只认那一个字段。
2. **退回人工绑定**：在服务端建一张 `平台会话 → 板子会话` 的映射表，平台写卡时按映射落库。丑，但演示当天最稳。

## 六、顺带发现的产品缺陷（不阻塞，但该改）

固件把所有 `code != 0` 统一渲染成标题「路线查询失败」，其中 `code=3`（还没有路线）其实是**正常空态**，不是错误。老人看到"失败"两个字会以为设备坏了。

建议改法（改 `route_card.cc` 的 `Parse()`，一行判断）：

| code | 现在显示 | 应该显示 |
|---|---|---|
| 3 | 路线查询失败 / 还没有查到路线 | **请先说要坐车去哪** / 手机上告诉小助手目的地 |
| 2 | 路线查询失败 / 缺少会话编号 | 会话没选好，请重新选择 |
| 4、5、6 | 路线查询失败 / 具体原因 | 保持 |

现在不改，是因为演示链路还没跑通，改固件会引入新的变量；等屏幕能出真卡之后再动。
