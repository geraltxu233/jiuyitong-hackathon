# 就医通 A/B 方案对比与下一窗口交付清单

> 2026-10-25 01:27 | 状态：**已选择 A 并开始执行**；本文保留决策依据与验收清单，实际进度以 `就医通_A方案上线与固件菜单验收_2026-10-25.md` 为准。
> A＝先上线当前 v3，不做动态最近医院；B＝先补最近医院工具，再上线完整流程。
> 本文先给对比结论，再给下一窗口可直接执行的清单。阅读本文不需要回看聊天。

---

## 一、结论先行

1. **A 能验证「语音选院 → 自动查公交 → 墨水屏出卡」，但不能声称实现了原流程的「最近＋最好」。** v3 用「专科优先＋综合方便」替代「最近＋最好」，这是能力降级，不是同一需求的不同说法。
2. **B 才能完整覆盖原流程的「最近＋最好」。** 最近由地图工具计算，最好由项目专科榜查表；两者必须分开返回依据，不能让模型凭印象合并。
3. **A/B 都不需要腾讯智能硬件定位 API，只要老人能口述起点。** 自动获取设备坐标才涉及 GPS、网络定位或企业权限，这是另一条能力，不是最近医院的必要前提。
4. **A/B 都不应恢复旧第 4～6 步。** 当前没有「到院按键事件 → Agent → 院内展示」链路，而且用户已明确旧的到院确认、院内展示、按键结束不适合现在使用。
5. **急症分支是有意的安全改版，不算流程不匹配。** 原流程让急症用户做两院选择；现版红档直接建议 120，黄档建议尽快急诊且不查公交，不应为了字面匹配原流程而退回去。

选择口径：只先验证现有语音与路线卡闭环，选 A；验收目标必须包含真实「最近＋最好」，选 B。**不要把 A 对外描述成完整实现。**

## 二、A/B 优缺点与能力边界

| 维度 | A：先上线当前 v3 | B：先补最近医院工具 |
| --- | --- | --- |
| 核心目标 | 尽快验证已有能力的新对话流程 | 补齐动态最近，再验证完整选院流程 |
| 主要优点 | 改动集中在提示词与 Agent 配置；外部调用少；故障面小；现有 `query_transit` 已端到端验收 | 起点可变时仍能给出真实最近；去掉静态远近假设；产品语义与原流程一致；长期可扩展 |
| 主要缺点 | 没有动态最近；老人问最近只能听降级话术；两方案含义被改变 | 要改后端、工具发现、提示词和验收；增加地图调用与失败路径；需补医院坐标/POI 数据并明确排序口径 |
| 动态起点 | 支持：老人选院后口述起点，工具解析 | 支持：同一个起点先用于最近计算，选定后用于公交查询 |
| 最近医院 | **不支持**，禁止模型估算 | 支持，但仅限工具实际覆盖的候选集与排序口径 |
| 最好医院 | 支持 4 个科室的项目专科榜；其他科无排名 | 与 A 相同，新增最近工具不会自动补全专科榜 |
| 两方案 | 专科优先＋综合方便 | 最近＋专科最好，才与原始语义一致 |
| 路线规划 | 现有腾讯公交路线，按步行分档、少换乘、耗时排序 | 完全复用现有能力 |
| 路线卡 | 选定医院后调用一次 `query_transit`，写当前语音 Session | 最近筛选阶段不写卡；老人选定后才调用 `query_transit` 写最终卡 |
| Agent 访问腾讯 | 不能直接访问，只能经 Connector | 同样不能直接访问；只是 Connector 多一个工具 |
| 自动硬件定位 | 不包含，也不需要 | 不包含，也不需要；口述起点即可 |
| 后端改动 | 无 | 有：新工具、候选数据、距离或耗时计算、错误处理、日志与测试 |
| 固件改动 | 原则上无；若新建语音 Session 且固件仍硬编码 DIRECT Session，才需同步并重烧应用分区 | 同 A；最近工具本身不要求改固件 |
| 演示可靠性 | 较高，复用已验收链路 | 取决于新增工具的实测；未验收前不能承诺与 A 同级 |
| 长期维护 | 仍会受「没有最近」限制 | 数据与计算留在后端，比写死提示词更可审计、可扩展 |

### 共同能力边界

- 「最好」目前只是项目整理的专科排名，覆盖心内、消化、骨科、肿瘤；不是综合医疗质量评价，其他科不能编排名。
- 公交规划不等于车辆实时到站；当前能力不提供实时车辆位置、拥挤度、号源、医生排班。
- 候选医院不是全上海任意医院。现阶段只有中山、市六、仁济东院、肿瘤医院徐汇院区四家核准数据；B 默认也只能在这四家里算最近，除非另扩数据源。
- 肿瘤医院是专科医院，常规骨科、心内科等不能只因距离近就推荐。B 必须按科室过滤候选，而不是纯距离排序。
- 仁济必须限定东院，中山和肿瘤也要使用核准院区，避免同名医院或不同院区导致错误距离与路线。
- A/B 都不做诊断，不恢复旧的到院确认与院内主流程，不替代急诊分诊。

## 三、与原流程逐步匹配度

| 原流程 | A 匹配度 | B 匹配度 | 说明 |
| --- | --- | --- | --- |
| 1. 开机自我介绍 | 匹配 | 匹配 | 保留简短自我介绍并问症状 |
| 2. 症状对话，判断急/非急 | 匹配且安全规则更完整 | 匹配且安全规则更完整 | 红/黄/绿三档；急症不进入普通选院与公交流程 |
| 3. 非急症采集信息、症状和位置 | 基本匹配 | 匹配 | 先听症状，再补四项；起点在选院时确认，避免无意义重复问 |
| 4. 给最近与最好两个方案，老人选择 | **部分匹配**：只有专科优先与综合方便 | **完整匹配**：最近由工具算，最好查专科榜 | 这是 A/B 的本质差异 |
| 5. 院外导航一页，少步行少换乘 | 匹配修订版 | 匹配修订版 | 自动调工具，语音报摘要，墨水屏看路线；不做旧的按键确认到达 |
| 6. 到院后科室展示 | 有意不做 | 有意不做 | 用户已说旧步骤不适合；当前也没有到院事件驱动 |
| 7. 按键结束 | 有意不放进 Agent 主流程 | 同 A | 路线说明完即停，硬件按键行为不冒充对话状态 |

**匹配结论：A 是修订版主流程的最小上线路径；B 是保留原「最近＋最好」语义的完整路径。两者对旧第 4～6 步的删除是一致的。**

## 四、B 开工前必须先定的两个口径

### 1. 「最近」到底按什么算

| 口径 | 对用户应说的话 | 注意 |
| --- | --- | --- |
| 地图距离最短 | 「距离最近」 | 与原「最近医院」字面最匹配；不能拿直线距离冒充实际路程，若只用直线距离必须明确 |
| 公交总耗时最短 | 「公交最快到」 | 不应叫「距离最近」；需要多次路线或距离/耗时计算，失败面更大 |
| 步行少、换乘少 | 「公交最省事」 | 这是现有最终路线排序原则，不是医院最近定义 |

未拍板前不要写死算法。若保留原流程语义，应把「最近」与「最快/最省事」分开命名。

### 2. 候选范围

- 默认：四家核准医院中，具备当前科室普通门诊能力的院区。
- 不建议：直接全量搜索「医院」后把最近任意 POI 当推荐结果；可能得到错误院区、卫生院、专科不匹配机构或未经核对的数据。
- 「全上海最近医院」与「四家推荐医院里最近的一家」是不同需求，对外话术必须一致。

## 十、B 专项验收用例

| 用例 | 预期 |
| --- | --- |
| 起点明确、科室明确 | 自动调用最近工具，返回候选与真实排序依据，无模型编距离 |
| 起点模糊或缺失 | 先追问，不调地图，不猜坐标 |
| 常规骨科/心内科 | 候选过滤不具备对应普通门诊的医院 |
| 仁济相关方案 | 全程限定东院，最近结果与最终公交终点院区一致 |
| 部分候选地图失败 | 明确「结果不完整」并降级，不宣称全局最近 |
| 最近筛选完成但老人尚未选院 | 不写新路线卡，板端不会误显示最后一家候选 |
| 老人选定医院 | 只再调一次 `query_transit`，最终卡写当前语音 Session |
| 老人改起点 | 重新计算最近，不沿用上次排序 |
| 地图全部失败 | 如实说未查到，可改按专科选院或稍后重试，不编结果 |
| 红/黄急症 | 不进入最近与公交工具，安全话术优先 |

## 十一、回滚与完成定义

### 回滚

- Prompt/Agent 出问题：恢复备份的 v2 配置并重新读取复核；若为此新建过 Session，还要明确板端切回哪个 Session，避免云端回了、板端没回。

- 任何回滚后都做一条「语音问路线 → 工具成功 → 同 Session 5 行卡 → 板端显示」冒烟，不能只看 HTTP 200。
- 固件只有在 Session 或固件配置确实变化时才需要动；仅烧应用分区 `0x10000`，不动 NVS、bootloader、分区表和字库。
