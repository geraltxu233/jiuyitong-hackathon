## 结论（已落地的三条）

1. 软件侧只有 **一条** 新增运行时链路：`GET /api/transit` 导航后端，其余全是数据准备与材料。
2. **契约不需要重新设计** —— 硬件侧 `route_card.h` 已定死 `{code, title, lines[], source}`，服务端把腾讯的 steps 拍平后填进去即可，固件零改动。
3. 通路的形态是 **同一个手机热点内的明文 HTTP**，不是公网 HTTPS。这一步决定了整条链路能不能跑通（见下）。

## 现有契约（硬件侧已实现，软件侧照此填）

```json
{
  "code": 0,
  "title": "去复旦大学附属中山医院",
  "lines": ["步行330米到车站", "在龙腾大道龙爱路上车", "乘浦西滨江1路", "开往南浦大桥方向"],
  "source": "腾讯地图 50分 换乘1次 23:33"
}
```

| 约束 | 来源 | 软件侧的含义 |
| --- | --- | --- |
| 路径 `/api/transit`、query `from=demo&to=hospital` | `WS_ROUTE_ENDPOINT` | **后端路由必须叫这个**，改路径就要动固件重烧 |
| 每行 ≤12 汉字，超长被截断不换行 | 注释 + H1 实测 | 后端自己截断，别指望固件换行 |
| 每页 5 行、最多 12 行、Up/Down 翻页 | `kMaxLines=12` + H1 用 7 行验过 2 页 | **可以给 6–12 行**，板子自动分页；不是"最多 5 行" |
| `source` 承载"来源 + 查询时间" | 字段注释 | 缓存写 `"缓存路线 10-24 09:12"`，不新增 `stale` 字段 |
| `code` 非 0 时用 `message` | 字段注释 | 错误也用中文短句，固件直接显示 |
| 单次 GET、阻塞 ≤8s、不重试 | `RouteFetch` 注释 | **后端必须 6s 内返回**，腾讯 3s 超时就给缓存 |

结论：**不改固件契约**。`stale`/`data_time`/`notice` 这类字段没必要，塞进 `source` 即可。

### 一屏出完：5 行的取舍（24 日 00:25 落地）

原方案 9 行 → 2 页，老人要按键才能看完。只做"合并乘X+坐N站、去掉开往方向"只能降到 7 行，还是 2 页，所以必须再砍两行：

| 顺序 | 行 | 处理 |
| --- | --- | --- |
| 1 | 开往…方向 | **全砍**（两行都砍，方向性由线路名与站序承担） |
| 2 | 乘 X + 坐 N 站 | **合并成一行** `乘浦西滨江1路坐3站` |
| 3 | 站间步行换乘 | 超行时先丢 |
| 4 | 在 X 上车 | 超行时次丢（前一行已说"到车站"） |
| 5 | 到 X 下车（末段） | 超行时最后丢 |
| — | **到 X 换乘** | **永不丢**，全程唯一会迷路的点 |
| — | 首段/末段步行 | 永不丢 |

结果：

```
步行330米到车站
乘浦西滨江1路坐3站
到瑞宁路龙腾大道换乘
乘徐汇滨江环线坐4站
下车步行250米到院
```

代价要如实承认：**上车点名称和末段下车站名被省略**。老人靠"坐 3 站/4 站"计数上车与下车，靠换乘站名确认换乘。若日后能改固件行高或字号，这五行的信息量还有余量。

### 选路的三个反直觉结论

| 结论 | 证据 |
| --- | --- |
| 单策略不够，必须两个都查 | 只用 `RECOMMEND` 会漏掉 `LEAST_TRANSFER` 里的好方案（人民广场那条从 45 分掉到 65 分）；两个策略合并去重后再排序，代价是多一次 HTTP（合计 <1s） |
| 步行不能按米数硬排 | 会出现"为省 57 米多花 20 分钟"的方案，改成 **200 米分档**，同档内比换乘与耗时 |
| 路线随时段变化 | 00:23 抓的样本里 49 路已收班，腾讯改给地铁方案；**白天演示的比例与线路会和凌晨不同**，排期时不要拿凌晨结果当基准 |

### 腾讯公交接口的三个实测结论

| 结论 | 证据 |
| --- | --- |
| `policy=LEAST_WALK` **不可用** | 返回 `status=348`（参数错误），该取值不认 |
| `policy=LEAST_TRANSFER` 对老人不友好 | 5 条方案全是"1 段公交 + 步行 1715–3021 米"，等于让人走 1.7 公里 |
| 正确做法：`RECOMMEND` + 自己排序 | 按「步行米数 > 换乘次数 > 总耗时」排序，挑出步行 585 米的方案；另需排除标题含"夜"的线路（夜宵线白天不开） |

## 历史卡点（已解除，留作记录）

当时的判断是"板子能不能访问到后端"，`WS_ROUTE_ENDPOINT` 写着 `http://192.168.4.2:8000` —— 那是板子自己配网热点的网段，正常联网态下不可达。

| 方案 | 结果 |
| --- | --- |
| A 局域网 HTTP（板子与 PC 同热点） | **成立**，已采用。零证书、零 TLS 内存 |
| B 公网 HTTPS | 未采用。板子 TLS 要 ~32KB 连续内存，通话期间必定不够 |

实际落地方式：**PC 接入板子所在的 MEIZU 热点**（而不是让板子换网），板子侧零改动。需要注意 Windows 把该热点判为「专用」网络，而 python 的入站放行规则只覆盖「公用」，需要补一条 `profile=any` 的 8000 端口规则。
