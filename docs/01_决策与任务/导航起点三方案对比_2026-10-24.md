## 3. 共同前提：现在的起点是"死的"

三条方案都要先知道这件事，否则会白改。

### 3.1 后端收到 `from` 但不用

`backend/route_server.py`：

```python
# 408 行
def _route(self, query):
    origin = (query.get("from") or [""])[0]     # 只做非空校验
    target = (query.get("to") or [""])[0]
    if not origin or not target:
        return self._send_json({"code": 2, "message": "缺少起点或终点"})
    ...
    lines, duration, transfers = query_route(self.key)   # ← origin 没传进去
```

真正决定起点的是模块常量：

```python
# 43 行
ORIGIN_NAME = "西岸国际会展中心"
ORIGIN = "31.162751,121.462919"

# _fetch_routes 里
data = tencent_get("/ws/direction/v1/transit/", {"from": ORIGIN, "to": DEST, ...}, key)
```

**所以 `?from=demo` 里的 `demo` 是个装饰品。** 换个值，返回的路线一字不变。

### 3.2 固件里的 URL 是编译期宏

`route_card.h:26`：

```c
#define WS_ROUTE_ENDPOINT "http://192.168.219.100:8000/api/transit?from=demo&to=hospital"
```

`route_card.cc:135` 直接把它塞进候选数组：

```c
const char* const candidates[] = {WS_ROUTE_ENDPOINT, WS_ROUTE_FALLBACKS};
```

**没有任何运行期拼装**。方案 1/2/3 只要想让 `from` 变，就必须先把它重构成"host 列表 + 路径模板 + 运行期 from"，这是三条路共同的第 0 步，别指望改个宏就完事。

### 3.3 契约不能动

板端解析的是 `{code, title, lines[], source}` 四个字段（`route_card.cc` 的 `Parse`）。三条方案都只允许**换 `source` 的文字**，不许加字段、不许改 `lines[]` 结构。加字段就要重烧全量固件并有兼容风险，没有收益。

## 4. 方案 1：按键选起点（推荐先做）

### 4.1 用户看到什么

菜单第 1 项「去医院（查坐车路线）」→ 先出一页「您现在在哪」，6–8 个预置地点，上下键选、中键确认 → 进大字路线卡。标题改成「从西门去中山医院」，让老人一眼确认起点没选错。

### 4.2 后端改动（约 30 行）

| 步 | 改哪 | 改什么 |
| --- | --- | --- |
| 1 | `route_server.py` 常量区 | 加 `PLACES = {"demo": ("西岸国际会展中心", "31.162751,121.462919"), "gate_west": ("住院部西门", "..."), ...}`。**保留 `demo` 作为默认键**，现有 endpoint 行为不变 |
| 2 | `_route()` | `name, coord = PLACES.get(origin, PLACES["demo"])`，把 `coord` 往下传 |
| 3 | `_fetch_routes` / `collect_routes` / `query_route` | 各加一个 `origin` 形参，共 3 个签名 4 个调用点 |
| 4 | 缓存 | **必改**：`cache_route.json` 现在不记起点，换起点后会端上一条"从旧起点算的"路线，且屏上看不出错。加 `"origin": origin`，读取时键不匹配就丢弃 |
| 5 | `title` | `"从" + name + "去" + DEST_NAME`。56 px 一行 7 字，两行上限 14 字，够 |

### 4.3 固件改动（约 80–120 行）

| 步 | 改哪 | 改什么 |
| --- | --- | --- |
| 1 | `route_card.h` | `WS_ROUTE_ENDPOINT` 拆成 `WS_ROUTE_HOSTS`（IP 列表）+ 路径模板；新增 `void RouteStartAt(RouteCard*, const char* from)` |
| 2 | `route_card.cc` | `HttpGet` 前用 `snprintf` 拼 URL；`s_from` 存当前选择（默认 `"demo"`） |
| 3 | `epaper_wifi.cc` | 新增 `Page::kOriginList`，直接抄 `DeptList` / `PublishDeptList` 那套（`kDeptRowsPerPage`、`dept_cursor_`、`screen.selected`），把数据源换成静态地点数组 |
| 4 | 菜单 | 第 1 项从"直接查路线"改成"进起点页"；或保留原行为、加第 7 项「换个起点」——**菜单一屏能放 10 行，加第 7 项零成本，推荐后者**（演示时不会被迫多点一次） |
| 5 | NVS（可选） | 记住上次选的起点，`ws397_wifi` 命名空间加一个 `origin` 字符串 |

起点列表建议就 3–4 个，别贪多：医院场景里老人只可能在「大门 / 西门 / 地铁口 / 公交站」这几处。**每个名字 ≤ 7 个汉字**（56 px 标题一行 7 字、40 px 列表一行 11 字）。

### 4.4 验收

```bash
# 1. 后端换起点，返回的路线必须变
curl "http://127.0.0.1:8000/api/transit?from=demo&to=hospital"
curl "http://127.0.0.1:8000/api/transit?from=gate_west&to=hospital"
# 两段 lines 应该不同；如果相同，说明 origin 没透传

# 2. 换起点后缓存不能串
curl "http://127.0.0.1:8000/api/transit?from=gate_west&to=hospital"   # 先请求一个
curl "http://127.0.0.1:8000/api/transit?from=demo&to=hospital"          # 再请求另一个
# 两条的 source 都应是"腾讯地图"而不是"缓存路线"
```

板端：选不同起点，路线卡第一行的步行距离应该跟着变。

### 4.5 风险

- 唯一失败模式是"老人选错起点"。低成本兜底：路线卡标题写清「从西门去中山医院」，错了能自己发现。
- 后端 `PLACES` 的坐标必须人工核实到"门口"，不能用建筑几何中心（现有 `ORIGIN` 就是行人主入口，照这个标准）。

## 5. 方案 2：WiFi 定位

### 5.1 两条实现路径

| 路径 | 谁扫 AP | 固件改动 | 说明 |
| --- | --- | --- | --- |
| 2A 板端扫 | `esp_wifi_scan_start` | ~40 行 | 板子已在 station 模式，扫描会短暂中断连接；通话中扫会掉音频 |
| 2B 后端代扫 | PC 侧扫（`netsh wlan show networks mode=bssid`） | **0 行** | PC 与板子同处一桌时物理位置一致，成本最低 |

**无论哪条，都不许板子直连腾讯**：板端 TLS 要 ~32 KB 连续内存，通话期间必定不够。腾讯请求必须由 PC 后端代理（明文 HTTP 到 PC，PC 走 HTTPS）——这和现在公交接口的架构一致。

### 5.2 结构性硬伤（先读这段，再决定要不要投入）

1. **手机热点的 BSSID 基本不可能在腾讯指纹库里。** 腾讯的 WiFi 定位靠众包采集（有人装着腾讯地图 App 路过并上报过）。MEIZU 临时热点、随身 WiFi 这类 AP 生命周期只有几小时，被采集的概率极低。
2. **热点重启会换 BSSID。** 部分机型默认开启 MAC 随机化，每次开热点都是新 BSSID，即使今天被收录，明天也失效。
3. **IP 定位只到区级。** 腾讯的 IP 定位拿来兜底，精度是"上海市徐汇区"，对"从哪个门进医院"没有任何意义。
4. **失败是静默的。** 如果定位失败后自动回落到预设起点，屏上仍然是正常路线，看不出"这是猜的"。**所以只要做方案 2，就必须在 `source` 行写清「定位失败，按西门计算」**，否则比不做更危险。

**结论**：这条路的成败取决于"现场那个热点有没有被收录"，而这在写代码之前就能测出来——见 5.3。

### 5.3 开工前的证伪（30 分钟，不动代码）

1. 手机开热点，板子连上，记下**当前热点 BSSID**（手机 WLAN 详情页可见）。
2. 用后端那把 Key 调一次腾讯位置服务的 **WiFi 定位**接口。
   - **已核实（10-24 15:39）**：官方路径是 `POST https://apis.map.qq.com/ws/location/v1/network`，`Content-Type: application/json`，body 里 `wifiinfo` 为对象数组、每项 `{mac, rssi}`；官方明确"只上报一个 Wi-Fi 且无 GPS/基站时**无法定位**"。
   - 本机 `netsh wlan show networks mode=bssid` **能直接拿到 BSSID**（实测 `MEIZU` = `92:f0:52:19:33:04`，信号 100%，且当前**只扫到 1 个 AP**）。扫描这一环成立。
   - **实测返回 `status=121「此key每日调用量已达到上限」`**。同一把 Key 打公交 `/ws/direction/v1/transit/` 仍是 `status=0`，所以不是 Key 失效。
   - **控制台截图定案（10-24 16:05）**：配额管理里 `/ws/location/v1/network` 的官方名称是**「智能硬件定位」**，它的「调用量 已分配/总额度」与「并发量 已分配/总额度」**两栏都是 `-`** —— 即**从未分配过任何额度**，不是"今天用完了"。对照行「IP定位」`/ws/location/v1/ip` 是 `6,000/6,000`、`5/5`（100% 已分配）。
   - 因此 121 的确切含义是**额度为 0**，明天配额重置**不会**自动好转。
   - **「配额分配」弹窗定案（10-24 16:12）**：选中该接口后，弹窗直接写「调用量分配 **可分配额度 0 次/日**」「并发量分配 **可分配额度 0 次/秒**」。**账户池里这项就是 0，没有东西可分。**
   - 用户已把「IP定位」额度调低来试，仍然可分 0 —— 证明腾讯的额度是**按接口独立计量**的（官方 FAQ：「每个 Key 的每个服务接口的调用量」），**不是共享池，调低 A 不会给 B 腾出额度**。
   - 唯一可行路径：控制台「工单」申请试用（商务 3 个工作日内联系）或企业认证（0.5–1 h 审核，但认证后是否给这项额度仍不确定）。**两条都赶不上 10-25 演示 ⇒ 方案 2 本次交付范围内冻结。**
3. 看返回：
   - `status=0` 且坐标与现场误差 < 500 m → 继续做，走 2B；
   - `status != 0` 或坐标偏几公里 → **停**，直接走方案 1。

### 5.4 如果探测通过，实现顺序

1. 后端加 `POST /api/here`，body 收 BSSID+RSSI 列表，转腾讯，返回 `{lat, lon, accuracy}`。
2. `netsh wlan show networks mode=bssid` 在 Windows 10 1803+ 需要**系统位置权限**才返回 BSSID，先确认这台 PC 能拿到（拿不到，2B 直接死）。
3. 后端把坐标作为 `origin` 传给公交接口（透传改造同 4.2 的第 2–4 步，可复用）。
4. `source` 行三态：`定位成功` / `定位失败按西门计算` / `缓存路线`。

## 6. 方案 3：解析对话文本

### 6.1 数据从哪来

`components/agent_link/src/transports/wifi/cloud/cloud_realtime.cc:625`：

```c
} else if (strcmp(event, "transcript.partial") == 0 || strcmp(event, "transcript.final") == 0) {
    const cJSON* text = cJSON_GetObjectItemCaseSensitive(json, "text");
    if (s_cb.text && cJSON_IsString(text)) s_cb.text(text->valuestring);
}
```

`Application::ShowText` 接到 `text`，打印 `voice text: %s`，并送给 `ui_.Answer()` 上屏。

### 6.2 前提已实测（10-24 15:39，结论与原判断相反）

**原判断（现已推翻）**：这条通道只给"AI 说的话"。依据是实拍照片里屏上显示的是智能体的回复。

**实测结果：用户原话也在里面，而且很完整。**

COM6 240 秒窗口，短按中键起通话、说"我在西门"，日志原文（节选，`_refs/com_stream.py` 抓取）：

```
[213.21s] WS397.wifi: voice text: 我
[213.33s] WS397.wifi: voice text: 我在
[213.98s] WS397.wifi: voice text: 我在西
[213.98s] WS397.wifi: voice text: 我在西门
[213.98s] WS397.wifi: voice text: 我在西门。
[214.75s] WS397.wifi: voice text: 我在西门。
[214.95s] WS397.wifi: voice text: 您好
[215.15s] WS397.wifi: voice text: 您好，我是就医通，您哪儿不舒服？
```

前半段是老人原话（逐字增长的 partial + 带句号的终稿），后半段才是 agent 回复。**所以"至少包含用户侧文本"这一条成立，方案 3 不是无源之水。**

### 6.2.1 但真正的阻塞在这里：分不出发话方

| 事实 | 证据 |
| --- | --- |
| 两侧共用**同一个回调** `s_cb.text` | `cloud_realtime.cc:625–627`，partial 与 final 都进 `s_cb.text` |
| 只读 `text` 一个字段，**没有 role** | 同上；全仓 grep `role` / `speaker` 在 realtime 侧零命中 |
| `_refs` 里没有协议文档可查 | 只能靠打原始 JSON 才能确认平台是否下发了 role |
| **`response.started` 不能当门控** | agent 文本 214.95s 就到了，`reply started #1` 215.33s 才打，**晚约 380 ms** |
| **app 层无法绕过**（10-24 16:35 补证） | `s_cb.text` 全仓**只有 1 个调用点**（`cloud_realtime.cc:627`）；公开回调 `on_show_text` 签名是 `(const char* utf8, void* ctx)`，**参数里没有 role**。原始 JSON 在组件内部就被 `cJSON_Delete` 了，app 拿不到 |

**推论**：任何"靠事件顺序判说话方"的写法都会漏掉第一句回复的开头。想不改组件、只在 app 层自己解析原始 JSON 的路子**也已排除**（原始 JSON 到不了 app）。要可靠区分只剩一条路——**改 `cloud_realtime.cc`，把 transcript 事件的原始 JSON 打出来，确认平台到底有没有下发 `role`**。而这是共用组件（`ai-passport`、`m5stack`、`paper-s31` 同仓）。

工程上可行的兼容改法：**不动现有 `text` 回调**，新增一个可选的 `void (*text_role)(const char* utf8, bool is_user)`，只有实现了它的 app 才收到 role。这样另外三个 app 零改动、零回归。

### 6.2.2 一处曾怀疑、实测**未发生**的缺陷（留档，别再重复判断）

`ShowText` 直接 `ui_.Answer(text)`，没有分流，代码路径上**用户的部分转写会被写进"AI 回答"那个槽**（`epaper_wifi.cc:64–67`）。按代码推导，说话时屏上应该会闪出自己的话。

**实测：没有上屏。** 用户全程盯着屏幕，没看到"我在西门"出现。

原因推断：这一段转写只持续 **213.21→214.75s，约 1.5 秒**，而墨水屏一次刷新要 **2100–2400 ms**，中间状态还没画完就被 agent 回复覆盖掉了。**是刷新延迟恰好掩盖了它，不是代码作对。**

残留风险：说得更慢、更长（老人本来就可能停顿），这段文本停留时间变长，仍有可能被画出来。真要修，前提还是先拿到 role。演示前不必动。

### 6.3 即使拿到用户文本，还有三个坑

| 坑 | 说明 |
| --- | --- |
| 起点/终点判不开 | "我在中山医院门口"是起点，"我要去中山医院"是终点，两者都含"中山医院"。关键词匹配必错，上 LLM 就多 1–3 s 延迟，而板端总预算只有 8 s |
| 没有触发通道 | 现在的流程是"老人自己长按菜单去查路线"。要"说完自动跳导航页"，等于在固件里加一条"文本→动作"的隐式通道，误触发（比如 AI 说"您可以坐 49 路"）直接跳页，演示会很难看 |
| 口音与噪声 | 老人普通话 + 医院环境噪声，转写错字率不低；"西门"转成"新门"就抽不出来 |

### 6.4 结论（10-24 16:35 重算收益后更新）

前提**过了**——用户原话拿得到。但真正卡住的是**分不出发话方**，而分说话方要动共用组件，代价已经从"改 app"升级为"改组件 + 全仓回归"。

**更重要的是：把收益算准之后，方案 3 不值得做。**

| 对比项 | 方案 1（按键选起点） | 方案 1 + NVS 记住上次起点 | 方案 3（对话推断） |
| --- | --- | --- | --- |
| 老人操作 | 中键进页 → 上下键移动 0–7 次 → 中键确认 | 中键进页 → **直接中键确认**（选中项已记住） | 中键进页 → **直接中键确认**（选中项已预填） |
| 需要改共用组件 | 否 | 否 | **是** |
| 地名误判风险 | 无 | 无 | **有**（口音、噪声、"西门"→"新门"） |
| 判不开起终点的风险 | 无 | 无 | **有**（"我在中山医院门口" vs "我要去中山医院"） |

关键事实：**方案 3 并不是方案 1 的替代品，而是叠加在方案 1 的起点页之上。**它省掉的只是"上下键移动"，那 1 次中键确认还在。而 NVS 记住上次起点能做到同样的事，且零风险、零组件改动。

再往下一层：**医院导诊设备的老人，是从同一个方向走进来的**——他得先看到这台设备才能操作它。所以起点在同一个老人身上近乎恒定，NVS 已经覆盖了方案 3 想解决的绝大多数情况。方案 3 的独特价值只剩一个场景："老人今天换了入口，且自己不会改"。

**这个场景不值得用"改共用组件 + 语音地名识别"去换。**

所以：

- **建议关闭方案 3。** 不是因为拿不到数据，而是四条成本（改组件、判起终点、造触发通道、抗口音噪声）叠加，换来的收益已经被 NVS 吃掉了。
- **把方案 1 里的 NVS 从"可选"改为"必做"**，它就是方案 3 想达到的那半个效果，成本约 20 行。
- **如果仍想确认平台有没有下发 role**，投入上限 15 分钟：诊断构建只加一行 `ESP_LOGI` 打原始 JSON，只写 app 分区。有 role 也只是"以后可以做"，**不代表现在该做**；没有 role 就彻底删除这条路。

### 6.5 变体：让云端 Agent 自己提取（10-24 17:35 评估）

用户提的另一种架构：**不由固件解析文本，而由云端 Agent 从对话里提取起点/终点，再交给后端查路**。

**这个思路绕开了 6.2.1 的 role 问题**——Agent 本来就是对话的一方，它天然知道哪句是用户说的，不需要 `role` 字段。这是它相对方案 3 的根本优势。

但有三条硬约束，其中第一条直接否掉了"Agent 调后端"这个形态：

| 约束 | 证据 | 后果 |
| --- | --- | --- |
| **云端 Agent 够不着 PC 私网** | 后端地址是 `http://192.168.219.100:8000`（`route_card.h:26`），平台 `base_url` 是 `https://` 公网域名（`agent_link.h:181`） | **"Agent 主动调我们后端"物理不通**，除非把后端部署到公网 |
| 执行 HTTP 的只能是板子或 PC 后端 | 板子已有 `esp_http_client`（`route_card.cc:7/56/59`），现在就在打这条 URL | Agent 的角色只能是"提取并告知"，不能是"代理请求" |
| Agent → 板子只有文本通道可用 | `on_show_text`（板子已在收）；`on_command` 是 App 控制面触发；`on_actuate` 只有 channel+int32 | 要传结构化起点，得在**系统提示词**里约定标记，如 `[FROM:gate_west]`，板端匹配后剥掉再显示 |

**唯一可行形态**：

```
用户说话 → 云端 Agent 提取起点 → 回复文本尾部带 [FROM:xxx]
        → 板子 on_show_text 匹配标记 → 板子自己 HTTP 打 PC 后端 → 腾讯 → 显示
```

好处是不用改共用组件（只在 app 层做字符串匹配）。**关键前提：平台后台必须能自定义 Agent 的系统提示词**——固件侧没有任何 `system_prompt` / `persona` 配置入口（已 grep 确认），只能走平台控制台。**这个前提没确认之前，这条路一步都不能动。**

**收益判断与 6.4 相同**：即使技术全通，它解决的问题（少按几次方向键）NVS 已经覆盖了。区别只是"能适应老人换入口"，仍不足以justify 引入提示词依赖 + 标记泄漏到屏幕的风险。

## 8. 会牵连到的地方（最容易被忽略的两处）

### 8.1 缓存的起点不是键

`cache_route.json` 只有 `{lines, duration, transfers, at}`。换起点后如果不改缓存结构，第一次请求会拿到**上一个起点**的缓存（因为腾讯超时时直接 `load_cache()`），而 `source` 只写「缓存路线 xx:xx」，老人完全看不出错。**这是方案 1 唯一的"静默错误"来源，必须一起改。**

### 8.2 人设里的"由近到远"是焊死在旧起点上的

`docs/04_软件与数据/就医通_人设_v2_2026-10-24.md` 里有一句：

> 从近到远：中山、肿瘤医院、市六、仁济

这个排序是按**西岸国际会展中心**算的。起点一旦变成可变的（方案 2/3），这句话就可能是错的，而人设是静态文本、算不了动态距离。

三条出路，选一条，别不选：

| 出路 | 代价 |
| --- | --- |
| 起点仍锁在西岸（方案 1 的列表里把"会展中心"设为唯一默认项） | 方案 2/3 的意义被削掉一半 |
| 人设删掉那句话，改成"就近请询问现场志愿者" | 少一条卖点 |
| 排序改由后端算、随路线卡下发 | 要加字段，违反 3.3 的契约冻结 |

**这条是方案 2/3 真正的隐性成本**，比代码量重要。
