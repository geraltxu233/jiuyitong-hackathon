### 已定死的响应格式

```json
{
  "code": 0,
  "title": "去市第一人民医院（东院）",
  "lines": [
    "出小区东门向东走200米",
    "乘58路，开往人民广场方向",
    "坐6站，中心广场站下车",
    "下车向西步行200米到医院"
  ],
  "source": "腾讯公交 10:32"
}
```

- `code`：0 成功；非 0 时可用 `message` 给一句可直接显示的中文原因。
- `lines`：**每行宽度 ≤ 696 px**（汉字 56 px、数字与半角英文约 22–24 px）。
  换算成字数：**纯汉字 12 字，或 9 个汉字 + 5 个数字**。超长会被固件截断并加 `…`，
  **不换行**——换行会压到下一行，所以后端必须自己控长。
- `source`：数据来源与查询时间，直接显示在页脚；失败时放一句人话。
- 最多 12 行，超过 5 行按页分页。

### 上板前自检

```bash
python tools/check_route_card.py route.json
```

逐行打印实际宽度占预算的百分比，超宽、缺 source、标题为空都会报错，行数超 5 会警告"需要按翻页键"。
**后端把 JSON 发给我之前先跑一遍**，能省掉一轮"上屏才发现被截断"的往返。

### 截断的代价

截断在屏上只是一个 `…`，但丢的是语义：`末班车23:00，雨雪天班次可能延误`（848 px，121% 预算）
会变成 `雨雪天班次可…`，老人读到的是一个没有结论的句子。所以行长不是排版偏好，是内容正确性。

## 六、已修缺陷与实测数据

### D1 中英混排基线错位（已修，待复验）

**现象**：路线卡里 `200 米`、`乘 58 路`、`35 分钟`、页脚 `BOOT` 这些数字与英文整体上浮，看起来像上标。

**根因**：绘制时每个字形按"自己所属字体"的行高定位 —— `top = (font->line_height - font->base_line) - box_h - ofs_y`。中文 28 px 字体 ascent ≈ 28，Montserrat 20 只有 ≈ 20，两者行框顶部对齐后基线差 8 px，英文自然浮起来。

**修法**：一行里只要含汉字，全部字形统一按汉字字体的 ascent 定位；纯英文行保持原行为不动（避免影响已经好的主页与菜单排版）。`Text()` 与 `TextClipped()` 各一处，规则一致。

**教训**：这类问题只在混排时暴露，纯英文页面（主页）和纯中文页面（菜单）都看不出来，所以 H1 的第一版样例必须包含数字。

### D2 墨水屏刷新耗时（实测，不修）

| 场景 | 实测 | 说明 |
| --- | --- | --- |
| 局部刷新（fast waveform 0x6a / 0xd7） | **2042–2057 ms**（4 次采样） | 面板自身刷屏时间，代码只做了 48 KB SPI 传输 |
| 全刷（waveform 0xf7），大字页/切版 | **2444–2450 ms**（6 次采样） | 只比局部刷新多约 **400 ms（+20%）** |

结论：**2 秒是这个面板的下限**，不是软件拖慢；全刷的代价只有 400 ms，所以大字页走全刷完全划算，残影风险不值得为 400 ms 去冒。
可选的优化（每次刷新都做硬复位+软复位，约 200–400 ms）收益与全刷代价同量级，风险更大，赛前不动。
演示影响：每次换屏约 2–2.5 s，刷新期间按键被丢弃（防误触连跳），**返回键不受此限**，随时能退回主页。

### D3 BOOT 在科室页"看起来没逐级返回"（00:10 修，待复验）

**现象**：用户实测，从科室大字卡按 BOOT，屏幕直接回到主页（对话界面），中间的科室列表没出现。

**根因**：BOOT 是唯一绕过"按键门控"的键——当初为了"通话中随时能挂断"而刻意放行。但屏一次刷新要 2.45 s，按下去没有即时反馈，人必然会再按一次；第二次按下时 `page_` 已经切到列表、屏幕却还在刷，于是**又退一级**，直接落到主页。中间那层从没被画出来，看起来就像"没逐级返回"。

**修法**：通话态保持无门控（随时能挂断），纯页面导航则和其它键一样等屏幕刷完；刷屏期间的重复 BOOT 直接丢弃并打日志。同时给 `SyncAgent` 失败强制回主页的地方补了日志——那是另一个能让页面"自己跳回主页"的路径，需要区分。

**复验（10-24 00:12）**：慢按一次一屏，两次 BOOT 均 `stale=0` 被接受，层级为 详情 → 列表 → 主页，完全正确（见 H13 验收记录）。
**但这一次两次按键都没有触发门控**，说明当次是"等屏幕刷完再按"。所以原症状（一按就到主页）**最可能是连按**，而门控是防止再次发生，不是已经复现过的修复。要真正确认，得故意在刷屏期连按两次 BOOT，看日志是否出现 `stale=1` 且只退一级。

**已知边角**：若某次刷新**失败**，`displayed_` 会停在旧值 30 s（`retry` 退避期），门控会让包括 BOOT 在内的按键在 30 s 内失效。刷新失败从未在实机出现过，暂不处理；真的出现时优先修这里。
