# 云端 Agent 查路两路径评估

> 2026-10-24；状态：现行评估，尚未配置账号、部署服务或做新的实机验证。用户已明确软件同学具有已备案域名和服务器。

## 结论

建议选路径 2 的薄后端版本：自建服务负责会话授权、地图工具和路线卡存储，调用现成 TiDB Link 服务；硬件继续复用 Agent Link 的音频、WebSocket、Opus 和墨水屏代码。无需自部署完整 Agent 平台，也无需把所有音频先转发到自家服务器。

如果现用 Deotaland 的语音会话可以直接挂载同一个 Connector，路径 1 会更快，因为连语音授权来源也不用换。但目前源码和现有公开材料没有证明这一点。不能以“都使用同一实时子协议”推导账号、模板、会话和工具互通。

开发时效：优先复用现成音频链路，最大的未知是工具挂载权限和当前会话归属。运行时延：两种路径都涉及语音理解、Full Agent 委派、地图请求与显示，尚无实测，不能声称第二条必然更快。若“云端完成全部通信”指自家服务器中继全部音频，会增加工作量和网络跳数，首版不推荐。

## 仓库核验

用户所说 AgentTrack 在指定仓库中对应的公开名称是 TiDB Link，旧名 Agent Stack；未看到独立 AgentTrack API。仓库是接入指南，不是必须部署到你们服务器上的完整平台。

| 能力 | 文档结论 | 实施含义 |
| --- | --- | --- |
| 实时对话 | Realtime Model 听与说，工具任务通过 start_task 委派 Full Agent | 不必自己再接一套 ASR、LLM、TTS |
| 自建业务工具 | Full Agent 可调用 Template 引用的 Connector 工具 | 后端暴露 query_transit 一类 MCP 工具即可接地图 |
| 公网接入 | streamable_http 为平台调用开发者 HTTPS 服务 | 可使用已有域名反向代理一个 MCP 路径 |
| 内网接入 | tunnel 支持开发者服务器主动建立 WebSocket | 私网并非绝对不可接；多副本平台有路由限制 |
| 模板挂载 | 需同组织的 Console Template 编辑权限，当前无 Customer API 替代 | 单有 API Key 和服务器还不能完成闭环 |
| 生效范围 | Session 创建时冻结模板配置 | 挂载 Connector 后必须新建 Session |
| 转写身份 | transcript.partial 文档明确 role 为 user 或 assistant | SDK 未读取 role 不等于平台不提供；现用部署仍需抓字段确认 |
| 硬件下发 | Realtime 没有直接设备命令帧；设备通道由开发者建立 | 工具结果回到模型，不会自动成为墨水屏路线卡 |

上游版本声明：合同基于 2026-10-21 的 a32727a543c1b62a569efc177994a97bf6a7fbed。维护者明确写出：早前文本和语音验证不等于设备工具派发验证成功，必须在实际部署、新 Session 中验证。

## 两路径比较

| 项目 | 路径 1：保留现用语音会话 | 路径 2：自家后端管理 TiDB Link 会话 |
| --- | --- | --- |
| 语音与硬件代码 | 基本复用 | 音频引擎和显示复用，改授权与会话接入 |
| 起终点提取 | 当前 Agent 负责；须确认能用工具 | TiDB Link Agent 对话澄清后调用工具 |
| 工具配置可控性 | 当前网关是否开放未确认 | 文档明确支持 Connector，仍需账号权限 |
| 新后端 | 地图工具、结果存储、设备结果接口 | 左侧内容加会话创建、短期语音授权 |
| 路线卡回硬件 | 都需要新增结果交付机制 | 都需要新增结果交付机制 |
| 最快成立的前提 | 当前语音 Agent 可直接关联工具 | 有正确部署地址、组织权限、可用模型及 Console 权限 |
| 评估 | 权限确认后可以是最快捷径 | 当前证据下更明确可实施的主方案 |

两条路线并不互斥。Agent Link 是设备侧 SDK，TiDB Link 是 Agent 服务，二者可以组合。

## 最小架构（设计建议，不是平台现成接口）

1. 盒子继续负责录音、播放和屏幕；自家后端为设备取得短期 connectToken；盒子用现有实时引擎直连平台。
2. 用户说“我在西岸国际会展中心，要去中山医院”。Agent 收集城市、起点、终点；“西门”不完整则先问是哪家建筑的西门。确认地点后才执行查询。
3. Full Agent 调用后端 MCP 工具 query_transit，业务参数可为 city、origin_text、destination_text、travel_mode。工具名及字段均为项目设计建议。
4. 后端把地名解析成经核实的 POI 或 GCJ-02 坐标，再调用腾讯公交规划；沿用现有 build_lines 与适老排序。模型不编坐标、不编路线。
5. 后端把同一份真实结果返回给工具供 Agent 口述，并保存路线卡；盒子另行取回 {code,title,lines,source} 显示。保留四字段路线卡格式，任务 ID/版本可在外层接口或独立元数据中维护。
6. 首版先按键拉取当前会话最新卡片，验证后再加有界轮询或自建推送自动显示。轮询要测与实时语音并存时的 RAM/TLS 余量；不能由“公网可达”推导板端新增 HTTPS 一定可承受。

地图 Key、Org Key、User Key 和 Connector Key 只存后端。设备使用自己的凭据和短期 grant。Connector 通过已验证的 sessionId 映射定位设备，不接受模型任意指定 device_id，也不接受任意 URL。Call Context 中 callId 用于去重，避免一次任务重复生成卡片。

## 现有代码可复用与必改

- 可复用：Agent Link 实时音频编解码/流控、墨水屏排版、route_server.py 的腾讯请求与路线压缩。
- 必改：后端目前 ORIGIN/DEST 是全局常量，from/to 查询参数未真正透传；必须改成真实双端点并以城市、起终点坐标、交通模式等组成缓存键，不能仅搬到云端。
- 新增：MCP 包装、会话到设备映射、任务结果存储和设备获取接口。授权服务在路径 2 中也需新增。
- 现有 CONFIG_AGENT_LINK_REALTIME_DIRECT 能请求 /api/v1/.../realtime，证明部分底层逻辑可复用；但它把 User Key 编入固件，源码明确定位于测试，不能当作完整上线方案。
- 不应把 device-gateway 的 base_url 直接替换成 TiDB Link 地址；旧设备激活/MQTT与新会话授权不是同一套 API。

## 验证顺序与两人分工

软件侧先做：确认部署及权限 → 一个最小 MCP 工具 → Console 挂载并新建 Session → 文本对话触发真实工具 → 同 Session 语音触发真实工具。先不接地图也可用固定测试响应验证调度，但正式验收必须换真实腾讯数据。

硬件侧并行做：复用现有路线卡解析与显示，定义设备结果拉取方式，验证既有语音能否使用挂载工具的新 Session，再测授权接入、断线及内存。

最终验收：语音给出 A→B，工具日志显示正确参数，腾讯返回真实路线，盒子显示同一次请求；改起点、改终点后路线和缓存均正确；地点含糊先追问；无路线或超时明确报错，不复用其他任务的旧卡。

第一道决定性关卡：实际语音会话能否调用自建工具。此关未通过前，不承诺一晚完成或具体端到端延迟。

## 更正此前判断

- “匿名文本说明平台没有 role”不成立：文档明确有 role，SDK 当前丢弃它；现用部署字段待实测。
- “Agent 只能通过回复标记传起点”不成立：Connector 是正式结构化工具通道。
- “有公网后端仍只有板子能执行 HTTP”不成立：Full Agent 可通过 Connector 调自建后端。
- “NVS 等价于语音动态导航”不成立：记住上次地点不能获得当前地点，也不能代替多轮起终点确认；设备为随身卡套，先前固定入口假设未经证实。
- “域名必须从头申请备案”不适用于用户现有条件；此前一概认定演示前做不完没有依据。
