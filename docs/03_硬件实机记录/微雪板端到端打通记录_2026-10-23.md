# 微雪板端到端打通记录

时间：2026-10-23 15:26–15:33
设备：Waveshare ESP32-S3-ePaper-3.97（`WS-EPAPER-397`，固件 2.0.0）
链路：手机配网 → 平台激活 → 设备绑定 → MQTT 上线

## 一、配网

用户在 iPhone 上关闭蜂窝数据，连接 `WavePaper397-1901`，在配网页下拉列表中直接选择 `MEIZU`（该 SSID 实际含一个尾随空格，手动输入必然失败），提交后一次通过。

```text
agent_link.prov: portal: WiFi credentials submitted
agent_link.wifi: WiFi associated; waiting for IP
agent_link.wifi: provisioning succeeded; credentials saved
agent_link.wifi: provisioning portal closed; SoftAP down
```

关键点：凭据写入 NVS 后才关闭热点，因此该步成功即代表后续重启会自动重连。

## 二、平台激活

```text
W esp-tls: Failed to open new connection in specified timeout
E HTTP_CLIENT: Connection failed, sock < 0
W agent_link.api: POST /api/device-gateway/claim-code: connect failed — 重试
I esp-x509-crt-bundle: Certificate validated
I agent_link.api: activation code issued, valid 600s
```

首次请求因 TLS 建连超时失败，SDK 自动重试后成功签发六位激活码，有效期 600 秒。属正常网络抖动，不影响流程。

## 三、绑定与上线

用户在平台输入激活码并绑定 Agent 后：

```text
I agent_link.cred: bound — auth_key stored
I agent_link.cloud: agent configuration received (1413B)
I agent_link.app: [state] CONNECTED
I agent_link.app: [link] Online (phase=5)
I agent_link.cloud: online
I agent_link.mqtt: connected (task stack headroom 3828B)
I agent_link.mqtt: subscription 1 ready (QoS 1)
I agent_link.mqtt: subscription 2 ready (QoS 1)
I agent_link.clock: clock synchronised by SNTP
```

`auth_key` 已存入 NVS，Agent 配置 1413 字节下发完成，MQTT 命令通道建立，两个订阅就绪，时钟同步完成。

## 五、下一步操作

1. 长按中键约 1 秒，进入 `Conversations / setup`。
2. 按“下”键选中 `Create new conversation`，按中键确认。
3. 回主界面短按中键，屏幕显示 `Connecting voice...` → `Call active / listening`。
4. 说话验证上行与扬声器下行。

界面为英文，三向键中段为中键，BOOT 为返回/挂断，PWR 仅控制电源。

## 六、已知缺陷

- 配网页 SSID 靠 JavaScript 从下拉同步到文本框，iOS 受限 WebView 若不执行 JS 会得到空值并被 `required` 拦截。
- 配网 HTTP 服务 socket 会被反复探测耗尽（`accept (23)`），且无法自愈，只能复位。长时间反复访问后配网页将不可用。

## 七、实时语音实测（18:27:51 起，COM6 只读抓取 180 s）

### 7.1 完整链路证据

设备 uptime 以括号内毫秒为准：

```text
(48021)  [link] Online (phase=5)
(48651)  esp-x509-crt-bundle: Certificate validated
(50701)  realtime: WiFi power saving suspended for voice
(51431)  realtime: session.connect sent over WSS
(52691)  [state] READY / [link] Voice ready (phase=6)
(52691)  realtime: voice session ready (Opus 16 kHz up, Opus 24 kHz down, server endpointing)
(52711)  realtime: Opus encoder stack=PSRAM; internal free=128467 largest=53248
(62811)  reply started #1
(66801)  reply audio end #1 (started=1, interrupted=0)
(66801)  reply audio: Opus, 228 packets, 13680 bytes, 4560 ms PCM, max gap 353 ms
(66811)  reply processing: decode max 19777 us, sink max 5639 us, pacing max 0 ms
```

结论：**WSS 实时语音全链路打通**。`session.connect` → `session.ready` → 上行 Opus → 服务端 VAD 切句 → 回复 Opus 228 包 → 解码 → I2S 播放，全部有日志佐证，`interrupted=0`、`drop=0`。

### 7.2 协商参数（与协议文档交叉验证）

| 项 | 实测值 | 说明 |
| --- | --- | --- |
| 上行 | Opus 16 kHz | 与服务端协商一致 |
| 下行 | Opus 24 kHz，60 B/包，20 ms/包 | 60 B / 20 ms = **24 kbps**，与 tidblink 文档 `bitrate: 24000` 吻合 |
| 分段方式 | **server endpointing** | 不是按住说话，是持续通话 + 服务端判断句尾 |
| 上行带宽 | tx 6.0–6.1 KB/s ≈ 48 kbps | 相比 PCM16 16 kHz 的 32 KB/s 压缩约 5.3 倍 |
| 下行带宽 | 回复期平均 3 KB/s ≈ 24 kbps | 突发时窗口内可达 9.85 KB/s |

### 7.3 三个工程余量问题（不影响演示，影响长通话）

| # | 现象 | 判据 | 风险 |
| --- | --- | --- | --- |
| 1 | 编码单帧最坏 **21.8 ms** | 帧时长 20 ms → 占用 **109%** | 峰值已超实时预算；持续高负载时会积压 |
| 2 | 解码单包最坏 **19.8 ms** | 帧时长 20 ms → 占用 **99%** | 余量≈0；连续两包背靠背到达就来不及 |
| 3 | 到达最大空洞 **353 ms** | 4560 ms 音频内出现一次 353 ms 断供 | 叠加第 2 条，可听到断续 |

补充：`Opus encoder stack=PSRAM` —— 编码器栈在 PSRAM，访问延迟高于内部 RAM，可能部分解释 21.8 ms 的编码耗时；内部 RAM 尚余 125 KB（最大连续 52 KB），有搬回内部 RAM 的空间。

### 7.4 栈余量

日志字段顺序（`cloud_realtime.cc:148-167`）：`stack=<当前任务最小剩余>/<媒体任务栈>/<编码任务栈>`，其中第一项由 `uxTaskGetStackHighWaterMark(nullptr)` 取得，ESP-IDF 单位为**字节**。

```text
stack=452/16084/16484B
```

- 媒体任务栈 16084 B，编码任务栈 16484 B
- 最小剩余 **452 B**，且该值是在**打印这条日志的过程中**测到的（printf 多参数格式化本身占栈），说明峰值由诊断日志造成
- 判断：尚未溢出，但余量临界。若后续在该任务里加深调用层级（错误处理、TLS 重协商），有溢出风险

### 7.5 抓取方法（可复现）

设备空闲时不打日志——该 app 的 `ESP_LOG*` 只有 `W`/`E` 级（硬件初始化失败、音频不可用、输入队列满、字库缺失、刷新失败），**按键与界面切换没有任何日志**。因此只能用"通话中的周期性统计"来观察。

```bash
# 只读，不发送数据；脚本在 _refs/ 下
python _refs/com_stream.py COM6 180
```

COM6 身份：`\Device\USBSER000` → `VID_303A&PID_1001&MI_00`（Espressif 原生 USB Serial/JTAG），`MI_02` 为 WinUsb/JTAG。
