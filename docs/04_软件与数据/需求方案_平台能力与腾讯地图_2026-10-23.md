# 需求方案：三个平台能力 + 腾讯地图导航

> 2026-10-23 | 设备：WS-EPAPER-397 已通（WiFi + MQTT + WSS 语音全链路验证）
> 当前平台：`bot.deotaland.cn`

---

## 需求一：把音频 Turn / Skill / 文件用起来

### 先说清一个前提

这三个能力都来自 `tidblink-dev-guide`，属于 **Agent Stack / TiDB Link** 平台（`ventured-agent-stack.pingcap.cn`）。你现在板子连的是 **Deotaland**，两套独立部署。

所以"用起来"只有两条路：**Deotaland 上有等价能力**，或**切平台**。

### 先去控制台确认三件事（10 分钟，不用改代码）

| 要确认 | 在哪看 | 有 → 怎么做 | 没有 → 后果 |
| --- | --- | --- | --- |
| Agent 的指令/提示词能改吗 | 控制台 Agent 配置页 | 导诊话术直接写进去 | 大脑行为不可控，项目没价值 |
| 有知识库/文件挂载吗 | Agent 配置页或"知识"页 | 科室表当文件上传 | 科室表只能塞进指令，长表会挤爆上下文 |
| 有工具箱/MCP/自定义工具吗 | 控制台"工具"页 | 腾讯 API 可挂成工具 | 只能走设备直连（见需求二） |

**这三个答案决定后面所有设计，建议先去看。**

### 三个能力各自的真实用法

| 能力 | 在 Agent Stack 上怎么用 | 对导诊的价值 |
| --- | --- | --- |
| **音频 Turn** | `POST /api/v1/user/sessions/{id}/events` + 音频文件；或旧 API 的 `/turns/audio` 直传 wav | 说一句症状 → 一个结论，失败可整段重试。比实时通话更可控，但**需要平台 ASR 已配置** |
| **Skill** | 上传 ZIP（根目录含 `SKILL.md`）→ 版本化发布 → 挂到 Agent | 把"症状→科室"规则写成带版本的文件，可审计、可回滚，不是猜 prompt |
| **文件** | Session 文件 / User File，支持校验和与分片 | 科室表、楼层索引、门诊时间做成文件，Agent 读文件而不是靠记忆 |

**但如果你的目标只是"让 Agent 按科室表回答"，Skill 可能过重。** 10 个科室的小表，直接写进 Agent 指令就够，一天能做完。Skill 的价值在"规则会变、要审计、要多人改"，黑客松两天用不上。

### 切平台的代价（如果 Deotaland 三样都没有）

| 步骤 | 动作 | 卡点 |
| --- | --- | --- |
| 1 | 在目标平台注册 product | 不在你手里，要主办方给 |
| 2 | 改 `platform_config.h` 的 `DEOTALAND_PLATFORM_BASE_URL` | 一行 |
| 3 | 重新构建烧录 | 分段烧录，保留 NVS |
| 4 | 重新配网 → 激活 → 绑定 | 前面已踩过的坑要再走一遍 |

**注意**：改 URL 不迁移产品 ID 和设备里已存的凭据，等于从零开始接入。

## 需求二：腾讯网络定位 + 公交规划 → 导航上屏

### 结论：能做，但有四个硬约束必须先接受

| # | 约束 | 影响 |
| --- | --- | --- |
| 1 | **这块板没有 GPS** | 只能靠 WiFi 网络定位；需要周边 2–30 个 AP 的 `BSSID,RSSI` |
| 2 | **精度通常 50–500 m** | 决定"从哪条路出发"，不决定"站在哪个门口"。对公交规划够用 |
| 3 | **AP 稀疏场地可能直接失败** | 必须预置 2–3 个起点让老人选（你原方案 I2 已有此降级，保留） |
| 4 | **扫描会短暂影响当前连接** | 语音通话中扫描会掉帧。必须错开，等通话结束再扫 |

### 三条实现路径

| 路径 | 谁调腾讯 API | 设备要改什么 | 依赖平台能力 | 判断 |
| --- | --- | --- | --- | --- |
| **A 设备直连** | 板子自己 | 加 HTTPS 客户端 + WiFi 扫描 + JSON 解析 + 上屏 | **不依赖** | **推荐先做** |
| B 上报给 Agent 代调 | 平台 Sandbox | 注册 sensor 上报 AP 列表 | **强依赖**（要 Sandbox/Skill 里有脚本） | 等平台确认再谈 |
| C 自建后端中转 | 你的服务器 | 加一条自定义 HTTP 通道 | 不依赖，但要额外服务 | 备选 |

**推荐 A 的理由**：不赌平台有没有工具能力，不重烧已通的语音链路，最坏情况也只是这块功能失败而不影响主演示。

### 路径 A 的具体设计

```text
用户按键（长按下键）
   ↓
① 等语音会话结束（WSS 关闭，释放 TLS 内存）
   ↓
② esp_wifi_scan_start → 取 RSSI 最强 10 个 AP 的 BSSID + RSSI
   ↓
③ HTTPS POST https://apis.map.qq.com/ws/location/v1/network
   key=<KEY>&macs=<bssid,-rssi|bssid,-rssi...>
   → result.location.lat / lng / accuracy
   ↓ 失败或 accuracy>500m → 降级：预置起点菜单（家 / 社区医院 / 车站）
   ↓
④ HTTPS GET https://apis.map.qq.com/ws/direction/v1/transit/
   from=lat,lng&to=<医院POI的lat,lng>&key=<KEY>
   → 取第一条方案，抽 3 行
   ↓
⑤ 墨水屏整屏刷新 3 行大字
```

### 关键实现要点（按踩坑概率排序）

| 要点 | 说明 |
| --- | --- |
| **TLS 内存** | 实测内部 RAM 空闲 128 KB、最大连续 53 KB。多一条 TLS 要 ~32 KB 握手 + 收发缓冲，**通话期间必定不够**。必须"先挂断、再请求" |
| **复用现成代码** | WiFi 扫描的写法在 `wifi_provision.cpp:142`（`esp_wifi_scan_start` + `get_ap_records`）；HTTPS + JSON 在 `cloud_api.cc` 和 `cloud_json.cc`。都在这套 SDK 里，照抄结构即可 |
| **Key 不能裸放** | 至少做到：独立 Key、只开"网络定位+公交规划"两项、设每日配额、不写进日志。条件允许就让路径 C 代理 |
| **JSON 只取需要的** | 腾讯公交响应很大，设备端只解析 `routes[0]` 的线路名/站数/步行距离，别整包解析 |
| **栈** | 当前媒体任务仅余 452 B。新解析必须**独立任务**，栈给 6–8 KB，别加在语音任务里 |
| **超时** | 定位 + 公交两次请求串行，各给 5 s 上限，总上限 12 s；超时直接上屏"网络不好，请再试" |
| **医院坐标** | 别用 POI 名称搜索（多义），直接烧入医院正门的 lat/lng 常量 |

### 与你原 INTERFACE 的对应关系

| 原协定 | 现在怎么落 |
| --- | --- |
| I2 网络定位 | 保留，但**发起方从"云端"改成"设备"**（路径 A） |
| I3 公交规划 | 保留"云端做精简"的理念，但精简逻辑移到设备端，只解析第一条方案 |
| I4 科室表 | **不变**，仍是静态表；区别是现在可以塞进 Agent 指令而不是烧 Flash |
| I5 降级 | 新增一条：`code=6 定位精度不足` → 预置起点菜单 |

## 建议的执行顺序

| 顺序 | 做什么 | 为什么这个顺序 |
| --- | --- | --- |
| 1 | 去 Deotaland 控制台确认那三件事 | 10 分钟，决定需求一的所有后续 |
| 2 | 申请腾讯 Key（网络定位 + 公交规划权限） | 有审批时间，越早越好 |
| 3 | 把导诊话术写进 Agent 指令，先验"说心脏不舒服 → 回心内科" | 这是项目价值核心，管道已经通了 |
| 4 | 再做路径 A 的定位 + 公交 | 独立功能，失败不影响主线 |
| 5 | 最后才考虑切 Agent Stack | 只有需求一确实需要 Skill/文件时才做 |

**不建议现在同时做 4 和 5**：切平台要从配网重做一遍，会把已经验证的链路打回原点。
