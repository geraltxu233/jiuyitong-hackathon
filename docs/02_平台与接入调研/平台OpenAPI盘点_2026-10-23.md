## 一、60 条路径分五组

| 组 | 代表端点 | 用途 |
| --- | --- | --- |
| 设备网关 | `POST /api/device-gateway/{auth,mqtt-token,heartbeat,claim-code,bind-status,offline}` | 板子自己用的那套（SDK 已实现，不用碰） |
| 智能体与动作 | `POST /api/agents`、`GET/PUT/DELETE /api/agents/{id}`、`POST .../actions/{action_key}/execute` | **核心可编程面** |
| 文件（drive） | `POST .../drive/upload-intent`、`presign`、`complete`、`download-ticket` | 文件直传 |
| 设备/企业/虚拟用户 | `POST /api/devices`、`bind-agent`、`reset-key`、`/api/enterprise/**`、`/api/virtual-users` | 管理面 |
| 固件与文档 | `GET /api/firmware/list`、`check-update`、`download-url`、`/api/docs/**` | 固件中心 + 帮助文档 |

## 二、三个真正的发现

### 发现 1：`execute` 是统一动作分发器

```
POST /api/agents/{agent_id}/actions/{action_key}/execute
body: { "payload": {...}, "stream": true|false }
```

官方描述原文：

> 统一动作调用端点（流式与非流式全模态收敛）
> **支持 LLM（打字机）、VoiceChat、TTS、ASR、VLM 等所有智能体能力**
> 全程零持有数据库物理连接

**这就是你要的「音频 Turn」的等价物。** `asr` 做识别、`tts` 做合成、`live-chat` 做文本对话，全部收敛到一个端点，`payload` 是自由结构，`stream` 控制打字机模式。

### 发现 2：`drive` 是文件直传，且明确给硬件用

```
POST /api/agents/{agent_id}/drive/upload-intent
  → file_key, upload_url, upload_method, headers
POST .../drive/uploads/{upload_id}/parts/{n}/presign
POST .../drive/uploads/{upload_id}/complete
POST .../drive/download-ticket    # 短效防盗链
```

描述里写明：**"硬件终端（X-Device-Auth-Key）与 Web 前端（X-User-Info）通用接口"**。

**这就是「文件」能力**。科室表可以走这条路。

### 发现 3：人设可以 API 写入，不用手点 UI

`AgentCreate` / 更新用的 schema 里有：

| 字段 | 说明 |
| --- | --- |
| `prompt` | **"个性化补充系统提示词（最大不超过10万字）"** —— 就是编辑页那个「个性化补充人设」 |
| `capabilities` | "实例级覆盖的AI能力管道参数" —— 可以按实例改模型通道 |
| `custom_attributes` | "依据属性 Schema 填写的配置" —— wake_word / volume 那些 |
| `description` / `avatar_url` / `enterprise_id` / `virtual_user_id` | 常规字段 |

意味着我写好的那段人设**可以用一条 `PUT` 直接写进去**，不必复制粘贴。

## 三、但仍然没有「工具」

我把 schema 名全扫了一遍，`persona / prompt / instruction / tool / mcp / knowledge / rag / skill / template` 里，只有 `prompt` 命中（在 AgentCreate/Update 里），**没有任何 tools、mcp、knowledge、rag、skill 相关 schema**。

所以：

| 需求 | 结论 |
| --- | --- |
| Agent 自己调腾讯定位 / 公交 API | **做不到**。`execute` 只能跑平台预置的能力通道（LLM/VoiceChat/TTS/ASR/VLM），不是任意 HTTP |
| 上传科室表给 Agent 读 | 通道有（drive），但**它是不是知识源还没证据**，可能只是文件存放 |
| 自定义判断规则 | 能做，走 `prompt`（10 万字） |

**需求二维持原判：只能设备直连腾讯，或自建后端中转。**

## 四、一个必须靠鉴权才能确认的点

`action_key` 在 spec 里没有枚举，是动态的。SDK 里硬编了 `realtime_voice`（`cloud_platform.cc:228`），而控制台显示的能力名是 `REALTIME_VOICE` + provider `agent_stack / live-real`。

推测 `action_key` = 能力名小写（`realtime_voice`、`live_chat`…），但**LLM 和 ASR 的实际 key 值必须查 `/api/agent-types/{type_id}` 或 `/api/agents/{agent_id}` 才能确定**。这四个端点都要鉴权，我这边没有凭据。

**你在本机跑一条就能定论**（把控制台生成的用户平台密钥放进环境变量，别贴给我）：

```bash
export DK="<你的平台密钥>"
curl -s "https://bot.deotaland.cn/api/agent-types" -H "X-Api-Key: $DK" | python -m json.tool | head -60
curl -s "https://bot.deotaland.cn/api/agents/<你的agent_id>" -H "X-Api-Key: $DK" | python -m json.tool
```

输出里如果列出 `capabilities` / `action_key` 清单，我就能把 ASR / TTS / live-chat 三个动作的实际参数写出来。

鉴权头有四套：`Authorization`、`X-Api-Key` + `X-Api-Secret` + `X-Client-Id`（平台密钥三元组）、`X-Device-Auth-Key`（设备）、`X-User-Info`（浏览器会话）。

## 五、还有两个顺带发现，都跟你之前欠的验证项有关

| 端点 | 价值 |
| --- | --- |
| `GET /api/devices/{device_id}/mqtt/debug-token` | 能拿设备 MQTT 调试 token → **可以直接往板子下发命令做调试**，不用等按键 |
| `GET /api/firmware/check-update`、`/list`、`/download-url` | 平台有 OTA 通道 → 你那个"OTA 未验证"项有正规做法，不用自己搭 |
| `POST /api/devices/{id}/bind-agent` / `unbind-agent` | 换绑 Agent 可以脚本化，演示前切 Agent 不用点 UI |
