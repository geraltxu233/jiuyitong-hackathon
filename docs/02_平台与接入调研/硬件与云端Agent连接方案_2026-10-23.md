# 硬件与云端 Agent 连接方案

> 日期：2026-10-23  
> 适用硬件：工作区当前记录的微雪 ESP32-S3-ePaper-3.97（ESP32-S3-WROOM-1-N16R8，16 MB Flash、8 MB OPI PSRAM、800×480 墨水屏、ES8311 音频）  
> 依据：参赛方“先复用现成链路”流程截图、工作区 INTERFACE 与 Arduino 配置文档、此前对 Agent Stack 两代 API 及示例仓库的调研。

## 结论先行

**先按参赛方给出的现成方案验证，不先写 MQTT、Connector 或 Realtime 固件。**先确认准确板型有对应固件，能通过 ROROLEE App 完成绑定和上云，再验证一次云端 Turn，最后验证板载输入触发并由同一块板显示或播报结果。每一步都有成功证据，才进入下一步。

当前不能断言这条链路已经可用：工作区只有板卡自检 sketch，没有业务固件；`/api/triage` 是联调草案而不是已部署服务；ROROLEE 的配对、传输和密钥协议没有从截图或公开资料中得到确认；赛事服务到底运行旧 Agent Stack API 还是新 TiDB Link API，也未从该部署实测。

### 方案选择

| 顺序 | 方案 | 使用条件 | 当前决定 |
|---|---|---|---|
| 1 | 参赛方现成板卡、匹配固件、ROROLEE App、Agent Stack | 主办方能给出准确板型对应的固件、App 操作和有效凭据 | **首选，先验证** |
| 2 | 我方后端代理 + 选定代际的 Agent API | 现成链路不能接入项目场景，且主办方确认了服务版本、密钥权限和接口 | 备选，另立工程任务 |
| 3 | Realtime WebSocket 或 Agent Tool/Connector 控硬件 | 基础闭环已稳定，且目标 API 代际确实支持、设备固件也有相应能力 | 暂不做，不作为首个演示依赖 |

## 推荐架构

分清初始化链路与业务数据链路。ROROLEE App 可能仅负责配网和绑定，也可能参与音频/消息转发；目前没有证据能确定是哪一种，所以先将其视为供应方黑盒，不臆测它使用 BLE、MQTT、HTTP 或 WebSocket。

```text
初始化 / 管理：
手机上的 ROROLEE App ──供应方配网/绑定流程（细节待确认）──> 准确板型 + 匹配固件

业务闭环：
用户按板载按键或对板载麦克风说话
        ↓
ESP32-S3 上的匹配固件采集真实输入
        ↓
供应方已支持的 Agent Stack 连接通道（协议与 API 代际待实测）
        ↓
Agent 完成一次判断，或调用一个已验证的工具
        ↓
最终结果沿受支持通道返回同一设备
        ↓
墨水屏显示结果；若板载音频链路可用，再播报
```

若 Agent 要主动触发设备动作，才需要额外的设备工具通道：

```text
Agent Tool → 已验证的设备工具接入层 → 设备现有命令通道 → 固件执行 → 状态/结果回报
```

**不要先把“Agent 判断后在设备上显示回复”误认为需要 Connector/MQTT。**只要现成客户端已能把最终回复显示在设备上，首个闭环不必让 Agent 反向控制硬件。屏幕显示可以是普通回复渲染，不等价于 Agent 调用显示工具。

## 首个作品建议

做一个收敛的“老人导诊信息卡”闭环：

> 用户提出一个具体症状问题 → Agent 给出非诊断性的建议科室 → 返回有限、结构化的结果 → 设备大字显示，并在语音输出确实可用时播报。

- 首版优先使用 Agent 判断，不强行添加硬件工具调用。如果现成开发 Skill/示例能确认 MCP 或 Tool 已可用，再增加一个只读工具（例如查询已整理的科室楼层信息）。
- 科室位置、楼层、门诊时间等事实应来自人工核对的静态表或明确的数据工具；不要让模型编造房间号、队列号或实时号源。
- 输出固定为少量短字段，例如：`科室`、`楼栋/楼层/诊室`、`提示语`。低置信度或无法匹配时转为“请到服务台咨询”；急症风险显示明确的急救提示，不给诊断结论。
- 墨水屏不渲染流式草稿。等待期间保留原结果页；只有获得最终结果时刷新一次。慢刷新状态不要反复整屏重绘。

## 分阶段验收与 Go/No-Go

### 阶段 0：锁定硬件和软件版本

向参赛方拿到并记录：准确板型/料号、固件版本或文件校验值、烧录地址和分区表、恢复/回滚步骤、App 版本、服务地址、API Key 类型与权限、配对步骤、官方示例版本。

- 工作区现有硬件说明是 Waveshare ESP32-S3-ePaper-3.97、N16R8，不应将“ESP32-S3”泛化成固件兼容证明。
- 当前 `firmware/00_board_check/00_board_check.ino` 仅检查芯片、Flash、PSRAM 和 I2C 应答，不包含麦克风录音、Wi-Fi、墨水屏业务页面、云端请求或音频播放。
- 不覆盖板上现有固件。烧写前保存原固件或确认官方恢复包和分区方案；只在确认准确匹配后烧录。

**Go：** 主办方确认该固件与准确板型兼容，且给出可恢复方案。  
**No-Go：** 只有通用 ESP32-S3 固件、缺少板级驱动/分区说明，或无法恢复；暂停刷写，先用官方硬件例程单独验证板子。

### 阶段 1：验证 ROROLEE 配网和在线状态

按官方演示完成配对、Wi-Fi 配置和绑定。记录 App/固件版本、设备标识、显示的在线状态、重启后是否自动重连。再关闭 App 或让手机离开网络，观察设备是否还能工作，区分“App 只负责初始化”和“App 是持续业务中继”。

**Go：** 设备能稳定上线且重启后恢复；明确 App 是否必须常驻。  
**注意：** App 显示设备在线只证明某种在线/心跳状态，不证明 Agent API、输入、结果回传和设备输出均已通。

### 阶段 2：独立验证云端 Agent

使用与当前服务版本匹配的主办方 Skill 和示例，先跑一次文本 Turn，确认项目/Agent/Session、鉴权、模型配置和成功终态。Gamma 指南是旧 `/api/**` 文档；`you06/esp32-agent-lcd` 也使用旧 API 与 NDJSON；`tidblink-dev-guide` 描述新 `/api/v1/**`、SSE、Connector 和 Realtime。它们不是可混搭的一套接口。

- 以一次真实成功响应为版本证据，不以文档仓库改名、路径猜测或登录成功作为证据。
- API Key 只放在供应方 App/后端规定的安全位置；不要写进仓库、日志或分享文档。先确认 Key 类型和权限，不能把 Workspace 管理 Key 当作设备用户 Key 使用。
- 记录成功 Turn 的最终消息和状态，不把“请求已提交”“SSE/NDJSON 已连接”算作完成。

**Go：** 实际服务返回成功终态和有效最终回复。  
**No-Go：** 401/403、模型/Sandbox/ASR 配置错误或服务代际不匹配；先由主办方处理，不开始设备协议开发。

### 阶段 3：打通设备侧输入与输出

只选一个固件已经支持的真实输入：优先板载麦克风加实体按键；若板载录音未被固件暴露，使用固件已有按键/传感器事件，不要把手机输入冒充板载输入。输出先选墨水屏最终结果；再单独验证 ES8311 播放。

验收闭环：**设备触发 → 云端记录到该输入 → 对应 Session/Turn 成功 → 同一设备出现对应最终结果**。日志用 request ID、脱敏 device ID、Session/Turn ID、固件和 App 版本及时间戳关联；不得记录密钥或不必要的敏感症状原文。

**Go：** 端到端连续成功 3 次，并在重启后成功一次。  
**No-Go：** 只在 PC 终端收到结果、App 里能聊天、或设备在线但设备输入没有触发云端 Turn；都不是设备闭环。

### 阶段 4：稳定后才加一个工具

先确认参赛方现有样例是否已包含工具调用和设备命令接口。若有，加入一个只读、低风险工具，例如“查询本院已核对的科室位置”。如果要让 Agent 改设备状态，必须有命令确认、设备执行回执和状态核验，不能把“命令发出”当作“动作成功”。

只有当所选 API 代际和部署能力被确认后，再决定旧版 MCP Server 管理路径或新版 TiDB Link Connector；新版模板引用还可能需要 Console 操作。不要两套协议同时实现，也不要为首个演示自行发明 MQTT 命令协议。

## 失败时的退路

| 失败点 | 处理 |
|---|---|
| 无准确板型匹配固件 | 不刷通用固件；用板卡官方示例证明硬件能力，向主办方索取对应固件或换兼容板 |
| App 配网成功但 Agent Turn 失败 | 让主办方先确认服务版本、Key 权限、模型和服务健康；保持设备侧不变 |
| Agent Turn 成功但板载输入不工作 | 检查固件已支持的按键/麦克风输入；必要时缩小演示为单键触发，不修改底层协议 |
| 有 Turn 但无设备结果 | 先检查供应方结果下行/渲染配置；不要直接推断要加 Connector。可在已支持的 UI 通道显示最终文本 |
| 现成链路确实无法接入项目 | 再新建自有后端：设备只连我方 HTTPS API；后端持有平台 Key，统一做音频/文本适配、Turn 终态解析和结构化结果校验 |

自建后端是**单独的备选工程**，不是当前已有的 L0：工作区的 `/api/triage` 目前只是接口草案，没有对应服务器代码。若走这条路，先确认服务是旧 Agent Stack 还是新 TiDB Link，再选一套协议；旧 API 音频 Turn（若部署仍开放且 ASR 已配置）与新 API Realtime/SSE 的实现方式不同，不能照抄同一客户端。

## 手机依赖与项目叙事

参赛方建议明确使用 ROROLEE App。它与先前项目文档里“产品不依赖手机 App”的定位有冲突。建议分两种表述：

- **比赛开发/配置阶段：** App 可用于配网和绑定。
- **产品演示阶段：** 只有关闭 App 后，设备仍能独立完成输入、云端处理和输出，才可以宣称无需手机持续参与；否则应明确说明手机/App 是运行依赖，而不是隐藏它。

## 前文需要更正的判断

1. 前文把 `/api/triage` 写成“L0 保底”过于确定；它只是接口协定，当前没有服务器和固件实现。
2. 前文推断旧 API 音频 Turn 可能是最短路径，只能作为待验证分支；历史 OpenAPI 的能力不证明赛事现网仍启用，也不证明 ASR 已配置。
3. 前文给 Realtime 两天成功率、首响耗时及若干板级资源百分比等数字没有实际测量依据，不作为排期承诺或设计输入。
4. 前文提出可把 `esp32-agent-lcd` 的代码“抄进”当前板卡不恰当：示例硬件是 M5Stack CoreS3 LCD，当前是 Waveshare 墨水屏，显示驱动和音频/按键支持不同；上游仓库没有明确 License，不能直接复制分发。只参考其“等待最终 Turn 结果、串口握手和请求关联”等设计思路。
5. 前文把 Connector/MQTT/Realtime 当作潜在主线太早。当前主线应是验证参赛方已经提供的板卡、固件、App 和 Agent Stack 组合。
