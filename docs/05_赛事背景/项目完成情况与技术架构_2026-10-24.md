## 一、项目是什么（一句话）

一台给不会用智能手机的老人用的**语音导诊卡套**：按一下中键说话，云端 AI 听清症状、按急症三档（红/黄/绿）分诊、给出"最好"和"最近"的医院建议；选定后长按中键，3.97 寸墨水屏出一张**大字公交路线卡**（5 行一屏看完，不翻页）；到了医院，菜单选「院内科室位置」，屏幕出**科室楼栋楼层大字卡**。

硬件是微雪 ESP32-S3 墨水屏开发板；语音对话走 Deotaland 云平台；公交数据走腾讯位置服务；路线卡由自建后端生成。**本地+云端两条链路都已打通，当前唯一断点是"平台调用自建工具写卡"这一跳。**

**明确不做**（避免被问倒）：诊断、挂号、实时公交到站、GPS/基站定位、跨通话记忆。

## 三、软硬件技术架构（六层）

### 3.0 架构总图

见同目录 `技术架构图_2026-10-24.svg`。文字版分层如下：

```
[用户层]  老人（语音提问 + 三向键/BOOT 操作）
   │
[硬件设备层]  Waveshare ESP32-S3-ePaper-3.97（N16R8）
   ├ ESP32-S3 主控（16MB Flash / 8MB PSRAM）
   ├ ES8311 音频 Codec + NS4150B 功放（I2S 16kHz 全双工）
   ├ 800×480 墨水屏（逻辑竖屏 480×800，矢量中文字库 2.2MB 独立分区）
   └ 固件：ESP-IDF v5.5.5 + FreeRTOS + Agent Link SDK + 应用层
   │
[网络层]  手机热点局域网（明文 HTTP，演示链路） / 公网（TLS：WSS + HTTPS）
   │
[云平台层]  Deotaland：live-real 实时语音 + live-chat LLM + 智能体「就医通」（人设 v2）
            TiDB Link（待联调）：Full Agent → Connector（MCP，调 query_transit）
   │
[自建后端层]  云端路线卡服务（route_card_service.py，nginx+systemd+SQLite）
              局域网演示后端（route_server.py，腾讯代理+压缩+缓存）
   │
[外部服务层]  腾讯位置服务 WebServiceAPI（公交规划 / POI）
```

## 四、两条运行链路（谁走哪条、验证到哪一步）

### 4.1 局域网演示链路（回退路径，已真机验证）

```
板子(192.168.x.59) --明文 HTTP GET--> PC 热点后端(192.168.x.100:8000)
                                        │ --HTTPS+Key--> 腾讯公交规划
                                        ▼
                                   压缩成 5 行路线卡
                                        ▲
                                   墨水屏大字渲染
```

- 板端走明文 HTTP 是**内存决策**，不是疏漏：通话期间板内剩余连续内存不足 TLS 所需的约 32 KB；查询前固件先挂断通话释放内存。
- 局限：PC 在热点上是 DHCP，网段漂移需改 `route_card.h` 重烧——**该约束对云端路径已不成立**（见 4.2）。

### 4.2 云端会话链路（现行主链路，传输层已实机打通，差平台写卡）

```
① 老人按键说话 ──WSS(Opus)──> Deotaland 实时语音 ──理解/分诊──> 口述医院建议
② 平台 Full Agent ──MCP: query_transit──> 自建云端后端 ──HTTPS──> 腾讯公交规划
                                            │ 写卡（绑定 sessionId，callId 幂等）
③ 老人长按中键选「去医院」──HTTPS GET /api/route-card?session_id──> 同一张卡
                                            ▼
                                   墨水屏 5 行大字路线卡
```

| 步骤 | 状态 |
| --- | --- |
| ① 语音链路 | **已真机验证**（180 秒抓包） |
| ② 平台调工具写卡 | **服务端就绪，平台从未调用**——当前唯一断点，卡在 Template 挂载 + 新 Session |
| ③ 板端取卡 | **已实机验证**：DNS/TCP/TLS/证书链/nginx/200/JSON 全通（屏幕显示服务端 code=3 原文，44 字节指纹互证） |
| 架构收益 | 板端走公网域名出站 NAT，**热点 IP 漂移不再影响本链路**；卡片按 session_id 存云端 DB，与内网 IP 无关 |

## 六、接口契约（板端 ↔ 后端 ↔ 平台）

### 6.1 四字段路线卡（板端唯一渲染契约）

```json
{"code":0, "title":"去中山医院东院区", "lines":["步行330米到车站", "..."], "source":"腾讯地图 50分 换乘1次 10:32"}
```

- `code != 0` 时给 `message`（一句可直接上屏的中文）；失败不编数据，屏上永远不出现假路线。
- 空卡响应精确 44 字节：`{"code":3,"message":"还没有查到路线"}`——**板端串口 `bytes=44` 与服务端日志 `-> 44B` 互证，是最硬的链路指纹**。

### 6.2 会话路线卡接口（云端，已上线）

```http
GET https://keleshiyizhimao.com/api/route-card?session_id=<平台会话ID>
```

无额外 token，session_id 即凭证；直返 200 不跳转（板端禁用了自动重定向）；响应 ≤2048 字节。

### 6.3 MCP Connector 工具（平台→后端，待联调）

```json
{"city":"上海", "origin_text":"西岸国际会展中心西门", "destination_text":"复旦大学附属中山医院东院区", "travel_mode":"transit"}
```

规则：先解析 POI/坐标再查腾讯（模型不编坐标）；结果同返 Agent 口述并写卡；`sessionId` 定位、`callId` 幂等；地点含糊先追问不调用。

### 6.4 屏幕文案判读表（现场排障用）

| 屏幕显示 | 定性 |
| --- | --- |
| 5 行路线 + 腾讯来源行 | 全链路通 |
| 标题「路线查询失败」+ 正文「还没有查到路线」 | **传输层全通，只是该会话没卡**（离闭环一步） |
| 「网络不好，请再试」 | 传输层失败（看串口 `https: end err=`） |
| 「接口不存在」 | HTTP 404（nginx location 未生效） |

## 七、工程实践与质量保障

| 实践 | 内容 |
| --- | --- |
| 单一数据源 | 科室 JSON → 脚本生成 C 表；医院排名/人设示例为手抄，已知技术债已记录 |
| 失败不编数据 | `code!=0` 或字段缺失一律 `kFailed`，`source` 放可显示的原因 |
| 四层备份 | L1 git 标签 / L2 应用分区 bin（sha256 校验）/ L3 整片 16 MB 镜像 / L4 工作区 tar.gz；恢复入口与自检 6 步已文档化 |
| 幂等与一致性 | callId 幂等防重试重查；Agent 口述与屏幕显示共用同一张卡，杜绝"说 A 路线、屏上 B 路线" |
| 排障闭环 | 44 字节指纹、串口监听、服务端对账脚本、raw_log 存原始请求（不猜字段名） |
| 内存纪律 | 路线查询前先挂断通话（TLS 需约 32 KB 连续内存）；路线任务独立 8 KB 栈不借用语音任务（余量 452 B）；大结构全改 static |
| 适老化硬约束 | 5 行一屏不翻页；35/40 px 双档大字；压缩规则优先保换乘站名与首末步行 |

## 八、已知限制（对外如实说明）

1. 跨通话无记忆：流程必须单次通话内闭环（平台限制，人设已按此设计）。
2. 坐车路线目前只做「西岸会展中心 → 中山医院东院区」一对起终点；云端链路闭环后由对话动态提取起终点。
3. 不做定位：局域网链路起点为预设常量。
4. 不做诊断：只分轻重、只指科室，红旗一律转 120。
5. 人设余量仅约 148 字节（4096 网关上限）。
6. 断线重连、重启保持、OTA 未验证。
