# 就医通 · 老人导诊墨水屏卡

给不会用智能手机的老人做的医院导诊硬件：**按一下开始说话，说完症状，屏幕上出现一张能照着走的大字公交路线卡。**

不装 App，不扫码，不注册。全程只有一颗中键。

> 当前状态：2026 上海 AI 硬件黑客松参赛原型，已完成端到端实机验收，未量产，不可直接用于真实就诊。

---

## 一、它替代了什么

老人去医院的三步里，最难的不是挂号，是"从家到医院这段路怎么走、下车往哪拐"。

手机地图能查，但老人要：解锁 → 找 App → 打字或按住说话 → 在一屏塞满小字和图标的结果里找自己要的那几行。绝大多数人卡在第二步。

这块板子把这条路压成三个动作：

| 老人做什么 | 板子做什么 |
| --- | --- |
| 按一下中键 | 建立语音会话，录音上行 |
| 说"我从西岸会展中心去中山医院" | 云端 Agent 断句、追问、选定医院、调腾讯地图算公交 |
| 松手等一两秒 | 通话自动挂断，屏幕自己切到路线卡，5 行大字 |

路线卡不是模板套出来的，每次提问都是真实的路网查询结果。

## 二、系统组成

```
┌─────────────────┐   PCM16 16k 上行   ┌──────────────────────┐
│  ESP32-S3       │ ─────────────────► │  TiDB Link 语音会话   │
│  3.97" 墨水屏    │ ◄───────────────── │  (server endpointing) │
│  单键 + 麦克风   │   Opus 24k 下行     └──────────┬───────────┘
└────────┬────────┘                                │ 自动调用工具
         │ HTTPS GET                               ▼
         │ /api/route-card              ┌──────────────────────┐
         └───────────────────────────── │  route_card 服务      │
             （只读，取本次会话的卡）      │  query_transit → 写卡 │
                                        └──────────┬───────────┘
                                                   ▼
                                          腾讯地图公交路径规划
```

三层职责分明：

1. **端侧**只做三件事：录音上行、播放下行、按 `session_id` 拉卡显示。不做语音识别，不做路线计算。
2. **语音会话**负责听懂、追问、决定调哪个工具。断句由服务端做（`endpointing.mode=server`），老人不需要按"发送"。
3. **卡片服务**负责调腾讯地图、把结果压成"一行不超过 11 个汉字"的 5 行文本，按 `session_id` 落库。端侧之后只读。

这样拆的好处是：屏幕刷新慢、内存小都不影响识别质量；换模型、换地图供应商不用动固件。

## 四、跑起来

### 4.1 卡片服务（服务器侧，正式链路）

`handoff_route_card/` 是完整可部署件。**纯标准库，零第三方依赖，Python 3.8+ 直接跑**：

```bash
# 配置：TENCENT_KEY 与 CONNECTOR_KEY
cp handoff_route_card/app/.env.example handoff_route_card/.env
chmod 600 handoff_route_card/.env

# 手工起一次看有没有报错
cd handoff_route_card/app
python3 route_card_service.py --host 127.0.0.1 --port 8010 --db ../data/route_card.sqlite3

# 健康检查：看到 code=0 且 key=loaded 即为正常
curl -sS http://127.0.0.1:8010/health
```

长期运行用 `systemd/route-card.service`，对外用 `nginx/route-card.conf` 的两个 `location`。完整步骤见 `handoff_route_card/README.md`。

对外接口只有一个：

```text
GET /api/route-card?session_id=<会话ID>
```

响应契约（板端以此为准）：

```json
{ "code": 0, "title": "去复旦大学附属中山医院", "lines": ["…"], "source": "腾讯地图 50分 换乘1次" }
```

`session_id` 本身就是凭证，无额外 token。未知会话返回 `code=3` 加 `message`，空卡响应固定 44 字节 —— 这个字节数在排障时是很有用的指纹。

### 4.2 本机联调（无公网）

```bash
backend/start_backend.bat          # 监听 0.0.0.0:8000
```

板子走明文 HTTP 直连 PC。仅用于局域网调试：板端 TLS 握手需要约 32 KB 连续内存，通话期间不够用，所以正式链路必须走服务端 HTTPS。

### 4.3 固件

见 `yiijuntong-firmware` 仓库。烧录只写应用分区 `0x10000`，不动 bootloader、分区表和字库，NVS 里的配网信息与绑定关系保留。

## 五、几个不显然的设计决定

| 决定 | 原因 |
| --- | --- |
| 断句交给服务端，不做按键 PTT | 老人不会在"说完"和"松手"之间对齐节奏；按键 PTT 会切掉句尾 |
| 回复期间暂停麦克风上行 | 服务端生成长语音时 TCP 发送缓冲会被顶满，1 秒写超时直接拆掉 WSS。暂停上行 + 播放排空后恢复，是把背压挡在应用层 |
| 挂断后自动切页，不用长按菜单 | 实测老人看到"长按一次看路线"的提示后仍会反复按。既然卡已在云端就绪，挂断即出卡最省动作 |
| 卡片带版本号，通话中静默轮询 | 避免"屏幕还停在上一张卡"的错觉；轮询只读版本，不重复算路 |
| 无明确推荐科室时显示提示页 | 语音说"去服务台"，屏幕却列出科室楼层，是硬矛盾。宁可不给信息，也不给错信息 |

最后一条踩过坑：早期版本在"没定科室"时把全院科室列表铺上去，实机语音与屏幕直接打架。现在的规则是——没有唯一推荐科室，就只显示"请到一楼服务台问"。

## 六、安全与隐私

这是原型仓，请按"公开可读的原型"来理解它的暴露面。

| 项 | 说明 |
| --- | --- |
| 密钥 | 全部走环境变量或 gitignore 的本地文件。仓库内**不含**任何真实密钥；`handoff_route_card/.env.local`、`backend/tencent_key.txt`、全片 flash 备份均已忽略 |
| 域名 | `keleshiyizhimao.com` 出现在文档与接口示例中。该服务当前只提供只读卡片查询，`session_id` 即凭证，但域名公开后可被枚举探测 |
| 医院数据 | `四家医院_科室映射总表.json` 等为公开信息整理（医院名称、科室、楼层、候诊区），不含患者数据 |
| 患者数据 | 语音内容与症状描述进入第三方语音会话服务，仓库中**不保存**任何会话音频或转写原文；验收记录里只保留脱敏后的会话 ID |
| 长期凭据 | 早期验收固件曾内置私有 User Key 直连。**该做法不可用于交付**，正式方案必须由后端签发短时 `connectToken` |

如果要把这个仓库转成真正可部署的项目，第一件事是把域名与内网拓扑从文档里剥出去，第二件事是给 `/api/route-card` 加会话鉴权。

## 八、已知限制

- **「最近医院」未实现。** 当前只能"语音选院 → 查公交"，不能宣称"最近 + 最好"。人设明确禁止模型编造距离。
- **四家医院硬编码。** 中山、仁济、市六、肿瘤，科室表来自人工整理，未接官方号源。
- **墨水屏刷新约 2 秒**，不适合频繁翻页，所以交互刻意收敛成"一屏一件事"。
- **未做跌落/断电/断网恢复的长时间浸泡测试。**
- 语音链路的稳定性修复（上行背压）只经过单次长回复复测，样本量不足以宣称已关闭。
